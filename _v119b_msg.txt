V1.19 finalization: published_mono fix, re-frozen identity, zero-real-F audit 7/7

Two things were tightened after the first V1.19 commit, both found by my own audits rather than by
the review:

  * `publish_new` now stamps every JSON record with `published_mono`. The reader's ordering is
    (published_mono, name), so without it the ordering silently degraded to file-name order -- and a
    run directory legitimately holds SEVERAL immutable records of the same family (one per
    verification run, because records are never overwritten), which made "latest" arbitrary. The
    zero-real-F audit caught this by reading the WRONG readiness record.
  * new `scripts/tests/d3_l1_v119_zero_f_audit.py`: an independent read-only audit of the claim
    "no real F work has been executed". It imports no runner, no supervisor and no scorer; it counts
    the artifacts only a real forward could leave (slot rows, raw scores, phase records, model load,
    warm-up, identity tail, supervision, round) and re-hashes the frozen runtime watch set. It also
    requires the readiness record to be re-adjudicated rather than trusted. 7/7 PASS ->
    ZERO_REAL_F_WORK_CONFIRMED.

The persistence edit changed a watched runtime path, so the V1.19 identity was re-frozen (new
identity/forward-targets/identity-targets records, a new authorization template) and the V1.18 run
directory again correctly reports NOT_READY for identity drift, which is the intended behaviour for
"runtime source changed -> new execution identity required".

Readiness: READY_FOR_USER_SIGNATURE with runtime_watch_closed true (14/14 paths) and
real_F_forward_executed false.
