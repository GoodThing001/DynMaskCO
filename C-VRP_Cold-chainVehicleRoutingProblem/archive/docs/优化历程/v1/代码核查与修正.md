### 正确 VehicleState（重新明确）

`route=[]` 不等于 `closed`，应是 `ready @ current_node`（可继续接后续 reveal 客户）。只有真正 `current_node → depot` 且返回完成后才 `closed`。

```python
@dataclass
class VehicleState:
    vehicle_id: int
    status: str            # idle / ready / committed / returning / closed
    current_node: int
    ready_time: float
    current_load: float
    committed_next: int | None
    committed_finish: float | None
    mutable_suffix: list
    served_route: list
    dispatch_time: float | None
    return_finish: float | None
```

### 事件循环（正式版）

```python
while not done:
    next_reveal = get_next_reveal_time()
    next_service_finish = min(v.committed_finish for v in vehicles if v.status == 'committed')
    next_return_finish = min(v.return_finish for v in vehicles if v.status == 'returning')
    clock = min(next_reveal, next_service_finish, next_return_finish, horizon)
    advance_fleet_to(clock)
    reveal_orders_at(clock)

### 修正的结论

1. **13.53 不能锁死为 OR-Tools-RH reference**：当前 OR-Tools 非严格 event-driven + depot bug。应标 `diagnostic only / pending protocol repair`。可写「该数据全局可服务潜力高」，不写「strict-online OR-Tools-RH = 13.53」。
2. **68.8% 不只是 gate 中和**：是「顺序 auction + 过早关车 + 只有 reveal event」三者共同导致。
3. **20.75 vehicles 不能全归咎顺序 auction**：过早关车是主因之一。
4. **28.24 vs 13.53 不能写「2.1× cost gap」**：service-first 下两者不在同一 service level（68.8% vs 100%）。应写「diagnostic 协议下 DynMaskCO 在 completion 和 distance 上均被 dominate」。
5. **模型输出「逐位相同」与 cost 差 0.05 矛盾**：需加 `np.array_equal` 逐实例核对，精确统计 identical 实例数。
6. **edge logits 对称**（$L_{ij}=h_i^\top h_j$ 天然 $L_{ij}=L_{ji}$），无法表达方向偏好——模型在 TW 顺序任务上弱于 EDD 的结构性原因。进 Phase A 高优先级（$q_i^\top k_j$ 非对称 scorer），不改 R1。
7. **训练 teacher 是 clairvoyant feasible NN multi-route**，不是「NN from online state」——Fix B 应叫「NN-context diagnostic」，不是「训练/推理对齐已修复」。真正解决监督错位要到 Phase B（visible-only expert / DAgger）。

## R1.5 第三轮（2026-08-28）：controller semantics 修复 —— 物理事件 ≠ 重规划触发器

> 复核最新 77 文件归档后发现：当前协议是「每一次物理状态变化 → 重新求整个 suffix → 只执行一条边」，
> 把 OR-Tools（以及 MaskCO）变成了 one-step receding-horizon controller，产生 plan churn / fragmentation。
> 这是 OR-Tools cost=44 高于贪心（30）的根因，不是「OR-Tools 在 strict-online 下天然劣于贪心」。

### 核心概念修正

- **物理事件**（不变）：`E = Reveal ∪ ServiceCompletion ∪ ReturnCompletion`。
- **重规划触发器**（新增分离）：`D = Initial ∪ NewInformation(Reveal) ∪ PlanInvalidation ∪ PlanExhaustion`。
- **关键**：无新信息的 service completion **延续旧 plan**（pop mutable_suffix 下一个），不重新 solve；
  只有 reveal 才触发 recourse。这仍然严格 non-anticipatory（committed leg 不可撤销，动作只用当前 filtration）。

### 6 个拍板决策

| 问题 | 决策 |
|------|------|
| OR-Tools 定位 | 保留 classical baseline，但**暂时取消「强 baseline / ceiling」身份** |
| 事件语义 | 物理事件 Reveal∪ServiceCompletion∪Return 不变；重规划 = t0 + Reveal + PlanInvalidation/Exhaustion |
| 是否每 ServiceCompletion 都 solve | **否**（这是 plan churn 根因） |
| penalty 1e9→1e4/1e5 | **否决**（违 service-first）；改 lexicographic-safe penalty |
| 优先级 | 先修 controller，再回模型 utility；clean 50K 继续暂停 |
| random_seed=42 | 保留，但只是 reproducibility fix，不是 fragmentation fix |

### 数字不自洽发现（已确认 + 已修复）

服务器验证确认了预判：**`Avg duplicate = 73.25`（灾难性 stale-tail duplication）**，正是导师第八节预判的
「只 reserve committed_next、不 reserve mutable_suffix」导致的。根因链：

1. reveal 后分批重规划（idle/ready 立即，committed 车 service completion 后）；
2. 先重规划的车，其新 tail 里的客户不被 reserve（只 committed_next 在 reserved）；
3. 后重规划的车拿走这些 tail 客户 → 双车 plan 同一客户 → 重复服务。

**修复**（`strict_online_env.py`）：
- `get_reserved_customers` reserve 整个 plan（committed_next + mutable_suffix）。
- reveal 时清空所有车 tail（`mutable_suffix = []`），让旧 tail 失效，重规划后新 tail 再被 reserve。

新增 **#18 测试**（reveal stale-tail no duplicate），13/13 PASS。服务器复测重点：`Avg duplicate == 0`。

```

### 4.3 统一 incumbent 的 shape bug（P0-8）

首次实现 `incumbent_sols = sols.copy()` 用 beam 路线长度（105），搜索阶段 `sols = insertion.get_sols()` 变 C++ 长度（~100），`incumbent_sols[improved] = sols[improved]` shape mismatch 崩溃。改为 list 存每实例变长路线，最后 pad 重建：

```python
incumbent_routes = [sols[b].copy() for b in range(sols.shape[0])]  # init
# 搜索循环内
for b in range(sols.shape[0]):
    if improved[b]:
        incumbent_routes[b] = sols[b].copy()
# 循环后重建
max_len = max(len(r) for r in incumbent_routes)
incumbent_sols = np.zeros((sols.shape[0], max_len), dtype=np.int32)
for b in range(sols.shape[0]):
    incumbent_sols[b, :len(incumbent_routes[b])] = incumbent_routes[b]
```

### 4.4 TW 可行性矩阵方向（P0-9）

原 `ready_at_j = tw_start[:, None, :] + service_time[:, None, :] + travel_time` 用错了下标（`tw_start[j]` 而非 `tw_start[i]`）。修正为 `tw_start[i]+service[i]+travel[i,j] <= tw_end[j]`，4 处。

### 4.5 progressive reveal 特征未揭示（zeroed-features，2026-08-27）

原 dataloader 在 **t=0** 就把 future 节点特征清零（`features[..., 2:] *= vis`），`vis_k` 只改注意力掩码，从没把特征重新揭示。导致「刚揭示」订单（vis_k=1）在模型眼里是 `coords=0.5, demand=0, tw=0, temp=0`，其真实属性从未进过模型，动态训练信号退化。

修复：dataloader 改为 yield **未掩码**特征，掩码移到训练器按 `vis_k` 逐步做：

```python
# train_dynamic_cc.py loss_at_timestep（online_seq）
vis = vis_mask_t[..., None]
feats_masked = raw_features.at[..., 2:].set(raw_features[..., 2:] * vis)
feats_masked = feats_masked.at[..., :2].set(feats_masked[..., :2] * vis + (1.0 - vis) * 0.5)
feats_masked = feats_masked.at[..., :2].set(coord_normalize_visible(feats_masked[..., :2], vis_mask_t))
```

这样每个 timestep 新揭示订单的特征被真正恢复，future 节点清零 + 注意力门控（非预知）。
