# 冷链物理参数来源与校准计划

> 本文只建立现实校准的证据链和执行顺序，不修改当前 pilot contract、scale v2 或已完成的 DEV-GATE。当前所有数值仍为方法学 pilot，不能写成真实车辆性能参数。

## 1. 当前 pilot 参数

温区类别固定为 `0=常温、1=冷藏、2=冷冻`。这三个类别目前是算法实验层的温区代理，不等于三个已经选定的具体商品；现实校准前必须先为每类确定代表性货物、包装、装载密度和品质指标。

## 2. 证据等级与采用规则

参数来源按以下优先级使用：同一车型和工况的原始试验数据最高；其次是可复现实验论文和设备厂商规格；法规/标准用于定义允许范围与测试条件；综述只用于发现来源，不直接生成参数。每个最终参数都必须保存出处、样本/车型、环境温度、舱体尺寸、设定点、装载、开门制度、单位换算、拟合代码、置信区间和适用范围。

UNECE ATP 给出了易腐食品运输设备的分类、温度条件、保温与制冷能力测试框架，适合约束设定点、硬温度边界和设备测试条件，但不能单独给出本车型的动态 \(UA/C\)、输入功率或开门热量。[^atp] 厂商规格可以提供特定环境温度和回风温度下的净制冷能力，例如 Carrier 50XR 同一设备在不同回风温度下报告不同容量；这类“制冷量”不是电输入功率，不能直接填入 `cooling_power_kw`。[^carrier]

## 3. 热学与能耗参数的校准

### 3.1 集总温度模型

当前自然升温项实际使用

\[
T(t+\Delta t)=T_{amb}+[T(t)-T_{amb}]e^{-k\Delta t},
\]

因此 `heat_transfer_per_hour` 是等效 \(k=UA/C\)，不是箱体传热系数 \(U\) 本身。校准时应在制冷关闭、门关闭的受控阶跃试验中记录舱内多点温度、外界温度与装载状态；对每个温区拟合 \(k\)，并用留出的动态温度轨迹验证。若只有 ATP 的 K 系数或箱体 \(UA\)，仍需结合舱体/货物等效热容才能换算成 1/h。

Artuso 等人的冷藏车动态模型以 ATP 试验数据进行训练与独立验证，并显式考虑环境温度、车辆任务、太阳辐射和墙体热质量，可作为本项目“用真实温度轨迹识别集总参数，而非抄一个常数”的直接方法依据。[^artuso]

### 3.2 制冷能力、输入功率与 COP

现实标定必须区分三类量：制冷能力 \(\dot Q_{cool}\)、设备输入功率 \(W_{input}\) 和 \(COP=\dot Q_{cool}/W_{input}\)。当前 `cooling_rate_c_per_hour` 控制温度下降，`cooling_power_kw` 直接累计能耗，而 `cop_parameters` 只用于开门热恢复能耗；三者若分别从不同来源抄值会破坏能量一致性。

建议优先采集同一设备在多个外界温度、设定点和负载下的制冷能力与输入功率曲线，然后联合拟合 cooling rate、power 与 COP。电动冷藏车实验表明，在保持舱内条件相同时，外界温度升高会降低制冷能力与 COP、增加压缩机功率，因此最终模型至少要覆盖 ambient × set-point 的二维工况，而不能只用一条温差线性关系。[^zhao] 若缺少完整实验数据，可先使用厂商的容量表约束制冷能力，再用实测能耗或输入电流补齐电功率；不能用厂商的“Watts cooling capacity”代替 kW electricity。

### 3.3 开门热负荷与预冷

`door_heat_kwh` 应由门面积、开启持续时间、内外空气焓差、交换空气质量以及货物/壁面恢复过程确定。冷藏车综合能量模型把门开负荷、墙体换热、货物换热、辅助设备和制冷机作为独立热流，并用静态试验验证模型，适合作为字段拆分与试验设计依据。[^maiorino]

标定试验至少包含门关闭基线和多档开门时长/频次；分别记录瞬时温升、恢复时间和恢复期电耗。`door_heat_kwh` 由温升与等效热容拟合，`thermal_capacity_kwh_per_c` 由不同装载水平的热响应识别，`dispatch_preconditioning_energy_kwh` 则由车辆从环境温度拉低到设定点的独立电表积分得到。三者不可通过同一总能耗重复计入。

## 4. 品质动力学的校准

Arrhenius 参数具有明确的产品和品质指标依赖。实验研究指出，不同食品、不同劣变机制和不同指标必须分别建模；即使在同一种产品上，某些指标适合 Arrhenius 模型，另一些也可能拟合不佳。[^haouet] 因此不能为“常温/冷藏/冷冻”各找一个文献数值便直接当作通用食品参数。

### 4.1 代表性商品与品质指标

在拟合以前先冻结每个温区的代表性商品与主品质指标。例如，冷藏类可选择草莓或番茄的硬度/维生素/感官指标，冷冻类可选择鱼或虾的感官、色泽或 TVB-N。番茄实验显示颜色、硬度和失重的温度效应可由 Arrhenius 关系描述，但适用范围与低温伤害仍需单独处理。[^tomato] 冷冻鱼研究则在多种恒温与变温情形下拟合并验证不同品质指标，说明 frozen 类应使用冷冻温度范围内的数据和相应参考温度。[^fish]

### 4.2 参数转换

对选定品质指标，先确定零阶、一阶或其他表观反应模型，再在至少三个等温条件下估计速率 \(k(T)\)。只有一阶剩余品质模型与当前 `Q'=Q exp(-kΔt)` 一致；若实验指标采用零阶或有上下限的 fractional model，应先修改品质状态方程，不能只换参数。

若一阶模型成立，则把论文或实验中的 \(E_a\) 统一换算为

\[
\texttt{activation\_over\_r\_kelvin}=E_a/R,
\]

并将速率换算到 1/h。`reference_rate_per_hour` 必须是同一品质指标在 `reference_temperature_k` 下的速率。当前所有温区共用 4°C 参考点并不适合直接承接 frozen 文献；现实校准可以保留统一数学参考温度，但必须用 Arrhenius 方程正确外推，或在新合同版本中允许温区独立参考温度。

### 4.3 动态温度验证与不可售阈值

拟合必须留出变温轨迹验证，因为路线优化产生的是非等温暴露。冷冻鱼研究在变温场景验证了等温拟合的动力学模型；新的草莓研究也把反应动力学与 Arrhenius 方程结合用于 4–30°C 的动态物流温度。[^fish][^strawberry]

`unsalable_quality_threshold` 不能由模型方便性决定。它应绑定感官拒绝、法规安全阈值、理化阈值或业务验收标准，并记录阈值对应的品质指标。阈值只决定 `num_unsalable/salable`，而连续 `quality_loss` 的尺度也要与该指标一致。`product_value` 则需要业务价值或损失成本数据；没有业务数据时只允许作为明确标注的 sensitivity weight，不能称为经济成本。

## 5. 单位与运营校准

Solomon 风格坐标不是天然的 km，时间单位也不是天然的 h。应先固定现实区域尺度或生成器到真实里程/时间的映射，再联合检查 `distance_km_per_unit`、`hours_per_time_unit` 与 `speed_kmph` 是否满足距离/时间一致性。若 speed 只参与行驶时间而 distance/time scale 又各自变化，必须用端到端 trace 对账，避免同一换算被重复应用。

车辆容量 50 目前是算法数据单位。现实研究必须说明它代表箱数、托盘、质量还是体积，并检查“共享总容量 + 多温区”是否符合所选车辆布局。若现实车辆存在每温区独立容量、隔板或不同预冷状态，需要新运营合同，而不是只改一个容量数值。

## 6. 推荐的校准数据表

每条原始或文献观测整理为以下字段：

| 类别 | 必需字段 |
|---|---|
| 来源 | DOI/标准版本/厂商页面、访问日期、原始表图位置 |
| 设备 | 车型、箱体尺寸、保温等级、制冷机、温区数量 |
| 工况 | ambient、set-point、装载、车速/太阳负荷、门时长与频次 |
| 观测 | 时间戳、各点温度、制冷能力、输入功率/燃料、累计能耗 |
| 商品 | 品类、包装、初始状态、品质指标、阈值、采样时间 |
| 拟合 | 方程、单位、参数、标准误/CI、训练/验证划分、残差 |
| 映射 | 对应 contract 字段、换算公式、适用范围、限制 |

建议形成三套参数：`nominal`、`low-stress` 和 `high-stress`。主结果使用预注册的 nominal；其余只作 sensitivity，不根据方法胜负回调参数。

## 7. 重新冻结与实验隔离

凡是会改变 baseline 的 D/Q/E 分布或 hard feasibility 的参数，都要建立新合同/profile 版本并重新运行 baseline service audit 与 `freeze_coldchain_scale.py`。这包括单位尺度、速度、温度边界、传热、制冷能力/功率、COP、开门热、热容、预冷、Arrhenius、初始品质、品质阈值和价值权重。旧 scale v2 只适用于当前 pilot 合同。

现实校准使用独立 CAL-PHYS 数据；拟合过程不读取 DEV-GATE/VAL/TEST 的方法效果。校准完成后，应在新的开发数据上重做 scale 和 O0-CC 路线确认，再冻结后进入正式 VAL。不得为了让某个方法胜出而选择物理参数或权重。

## 8. 当前执行边界

正式 DEV-GATE v4 已完成（verdict=GO）。当前进入 **CAL-PHYS 现实校准**：可继续收集来源、建立字段表、拟合参数。拟合过程不读取 DEV-GATE/VAL/TEST 的方法效果，不把当前 pilot 数值写成已校准；任何会改变 baseline D/Q/E 分布或 hard feasibility 的参数都要建立新 contract/profile 版本并在新 DEV 上重做 scale 与 O0-CC 路线确认。正式 VAL 在 CAL-PHYS 与新 DEV 复核完成前不生成、不冻结、不查看。
