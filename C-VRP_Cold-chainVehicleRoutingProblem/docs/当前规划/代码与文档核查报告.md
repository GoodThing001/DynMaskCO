## v4 主线修正

论文目标现固定为“基于 MaskCO 改进并应用于动态冷链物流优化”。因此本报告中查出的冷链缺陷不再是删除冷链主张的理由，而是 **C0 blocking backlog**：

1. 将现有容量状态正式锁定为 pickup-to-depot，并新增订单级 cargo manifest；
2. 统一温度、品质、能耗与物理单位；
3. 把冷链状态接入 strict-online execution trace 与 snapshot；
4. 建立唯一 trace-level cold-chain evaluator；
5. 将 counterfactual teacher 从 terminal distance 扩展到 $Y_{CC}$；
6. 最终方法必须包含 event mask、masked action reconstruction 与 iterative refinement，不能停在 frozen encoder + MLP。

运营语义的源码依据是：`strict_online_env.py:194` 在客户服务后执行 `current_load += demand`，`:205-213` 返仓后载重清零并关闭；`action_contract.py:137-161` 和 `authoritative_evaluator.py:96-133` 都从零开始逐客户累加载重；当前没有 depot loading、reload 或订单级货物 ownership。因此 v4 主实验采用取货回仓，而不是把在途插单误写成仓库配送。

该决策还使旧品质方向失效：`generate_coldchain_data.py:164-175` 按 depot 到客户的累计到达时间预计算损失，`thermal_state.py:246-256` 也混入配送式“到达/卸货”解释；pickup-to-depot 应按取货完成到返仓的在途时间和真实 compartment temperature 计算。旧 weighted-completion-time/toy 结果只能保留为历史调试证据。

当前代码仍未完成上述闭环，所以“动态冷链主线已锁定”是研究规划结论，不是性能结论。

## 4. 2026-09-01 发现的 P0 级源码问题

> 状态说明：P0-1/P0-4 的比较与统计链、P0-6 至 P0-10 的 snapshot/action/teacher 基础设施已在 2026-09-02 修复并通过对应测试；以下保留原始发现用于追溯。当前阻塞项以 §10 和执行进度表为准。

### P0-1：B0 frozen-assignment comparator 仍可能改变 assignment

`scripts/baselines/b0_or_expert.py:73-96` 在两种情况下进入贪心回退：`k>8`，或 `k<=8` 但不存在完整可行排列。回退遇到第一个不可行近邻就 `break`，随后无论剩余客户是否为空都返回 `True` 和部分 route。

影响：名义上的 OR-fixed/frozen-assignment 可能漏掉原 assigned customers。因此 `G_fleet=17.9%`、`G_seq=-1.25%` 不能作为冻结论文数字。

必须修复：

- 仅当返回 route 覆盖 assigned set 且无重复时才 `feasible=True`；
- `k>8` 使用不允许 drop 的 TSPTW/DP/OR 求解器，或将该 state 标为 comparator infeasible；
- 保存每个 state 的 assigned/returned set、complete、TW、capacity、return 与 reason；
- 只在四个 comparator 同 service 的 paired 实例上计算 cost interaction。

### P0-2：旧 `recourse_regret.py` 没有实现文档定义的 conditional recourse

问题：

- `scripts/analysis/recourse_regret.py:27` 导入归档中不存在的 `solve_vrptw_ortools`；实际 baseline 提供的是 `solve_vrptw_from_starts`；
- `:122-127` 虽循环不同 epoch，却始终传 `committed_prefix=set()`；
- 只删除节点，没有保存车辆 anchor、ready time、load、committed leg 和 mutable route；
- 没有计算完整 `J_e^π-J_e^*`。

结论：该脚本不能用于 CostAware teacher。应新建 `counterfactual_action_utility.py`，从真实 event snapshot force action 后使用统一 continuation rollout 得到效用。

### P0-3：HFR 的理论有向 A 与训练 target 不一致

理论文档定义：

$$A_{ij}=\mathbb 1[i\to j\text{ adjacent}].$$

但 `scripts/training/train_hfr_m0.py:91-113` 把每条相邻边同时写成 `A[i,j]=1` 和 `A[j,i]=1`，且没有监督 depot→first 与 last→depot。推理 `hfr_replanner.py:154-170` 却使用有向插入增益，并大量依赖 anchor/depot 边。

影响：训练目标没有覆盖部署动作使用的边语义，S2/S3 的 route CE 改善不能证明部署所需的 insertion utility。

处理：HFR 已作为负结果冻结，不建议继续修 HFR 主线；但论文解释应写成“structural target 与 deployed local action 不对齐”，不能写成“route signal 本质上无用”。CostAware 直接监督可部署 action。

### P0-4：HFR service-first 统计和 fallback 不足以支持部分现有结论

`run_hfr_gate_a.py:125-136`：cost 只对 complete 实例求均值，但 paired delta 对全部实例直接计算。对于 complete<100% 的变体，两个统计使用不同口径。

`hfr_replanner.py:242-245`：unresolved 时回退 JF1-H；而 `joint_fleet.py:254-283` 的 `_greedy_sequence()` 可能停止并遗漏未访问 customer，返回值不报告遗漏。虽现有部分实验记录为 100% complete，但源码没有形成严格 no-silent-drop certificate。

影响：

- `g_only=24.97/100%` 与 `min_travel=25.92/98.4%` 不可按 cost 直接比较；
- 不能据此正式主张“G 带来 -0.95 downstream gain”；
- full/group_logit 等 incomplete 变体首先是 service Gate FAIL，cost 只可作描述。

### P0-5：历史独立 CostAware 方向没有实现

114 个文件中没有独立 CostAware model、action candidate builder、counterfactual utility generator、oracle、trainer 或 evaluator。该项记录的是 v3 源码事实；v4 已由 D-030 将 cost-aware 限定为 DynMaskCO-CC 的内部效用对齐机制，并把 M0 定位为表征探针。

## 5. P1 级问题

> 后续状态：P1-2 已由 P0-R 重跑复核，interaction 更新为 -1.7430，CI [-2.387,-1.104]；P1-1 冷链物理问题则在 v4 升级为当前 C0 blocking work。

### P1-1：冷链物理尚未闭环

- `thermal_state.py:156` 把 J 转 kWh 写成 `/1000`，应为 `/3.6e6`；
- 品质更新实际用 class constant `K_0`，与文档温度依赖 Arrhenius 叙述不同；
- `authoritative_evaluator.py:287-288` 对 execution trace 固定返回 `quality=0, energy=0`；
- `DynamicColdChainModel.compute_spoilage_matrix():130` 对归一化 `temp_class` 直接转 int，冷藏 0.5 会落为 0；
- `train_dynamic_cc.py:99-104` 在 future reveal channel 已清零后计算 adaptive `rt_mean`；
- `spoilage_lambda` 被接收和打印，但主 loss 只有 route CE。

v4 处理：这些问题全部升级为 C0 blocking tasks。冷链仍是论文核心对象，但在 physical model、trace evaluator、校准与 sensitivity 闭环完成前，不得运行或宣传主冷链结果。

### P1-2：2×2 interaction 目前应降为 provisional

文档记录 VAL32 interaction `-1.6151`，逐实例 bootstrap CI 不跨 0；但 `JF1H-assign+TSPTW` 复用了存在 partial-return 风险的 `solve_or_fixed()`，且本次未提供 `oracle_ceiling.csv` 验证四路 completion。

因此可用于决定研究方向，但修复 comparator 并复跑前不进入摘要/主结论。

### P1-3：teacher 是有限预算 OR 且允许 disjunction

OR-joint teacher 使用有限 time budget，并允许以 service-first penalty drop 节点。HFR/JF2 对 `teacher=-1` 的客户不监督，可能产生 selection bias。必须报告 teacher coverage、drop reasons、budget sensitivity 与 action candidate coverage。

### P1-4：Gate 脚本缺少正式统计

现有 Gate 主要报告 mean、median、win/tie/loss，未在脚本中统一输出 paired bootstrap CI、Wilcoxon/paired permutation、effect size 和 multiple-seed aggregation。正式实验需补齐。

## 7. 最终判断（v4）

方向可以继续，但不能直接训练一个 utility head 就进入正式实验。当前正确顺序是：

1. 完成 C0 的单位、冷链状态、运营语义、snapshot 和 trace evaluator 闭环；
2. 在共同 Action Contract 上运行 O0-D 协议 sanity 与 O0-CC 冷链效用 oracle；
3. oracle 有足够 headroom 后才训练 M0 frozen-MaskCO 表征探针；
4. M0 可学后实现包含 event mask、效用对齐 masked reconstruction 与 iterative refinement 的 M1；
5. DEV Gate 成立后再做 MaskCO 身份归因、冷链机制归因、多 seed、稳健性和一次性 TEST。

v4 后论文核心固定为：

> Utility-aligned causal masked generation for dynamic cold-chain vehicle routing.

冷链物理本身不必宣称理论创新，但冷链状态、目标和 trace evaluator 必须作为 DynMaskCO-CC 的方法与证据闭环；CostAware 仅是内部效用对齐机制。

## 8. 第二轮重构新增的 P0 结论

### P0-6：现有 state archive 不足以恢复 insertion 语义

`collect_assignment_states.py` 保存的核心 route 表示为 `tail_mask[S,K,N]`。它能表达“客户属于哪辆车的 mutable tail”，但不能表达每辆车 tail 的先后次序。

CostAware action 是 `(slot, insertion position)`；位置依赖 predecessor/successor，continuation 也依赖完整有序 route。因此：

> 旧 assignment-state NPZ 可以用于 JF2 的集合分类，但不能直接用于 CostAware teacher、oracle 或 snapshot resume。

必须建立 `RecourseSnapshotV2`，至少保存 ordered executed prefix、committed leg、ordered mutable suffix、vehicle anchor/clock/load、event queue 和 RNG/tie-break state，并通过 round-trip exact parity。

### P0-7：strict-online 环境缺少正式 resume-from-snapshot 接口

现有源码包含 event execution 与部分诊断性 force/plan 操作，但没有一条已验证的 `snapshot → clone/resume → force full-fleet action → common continuation` 权威链。旧 `force_suffix` 一类接口不能替代完整状态恢复。

影响：如果直接从简化 NPZ 重建状态，teacher label 可能混入不同 clock/load/committed plan，得到的不是同一 state 的 counterfactual comparison。

### P0-8：动作必须作用于完整 fleet plan

插入一个客户时，合法 transition 必须保留其他 slot 的 route、executed prefix 和 committed leg。若接口只生成被修改 route，再由 evaluator 拼装，容易造成 plan overwrite、漏客户或双重服务。

因此新 action API 必须返回 full-fleet plan，带 customer-universe/uniqueness assertion，并以 no-op/incumbent exact parity 作为 Gate。

### P0-9：离线状态分布不能代替 on-policy 验证

如果 teacher 只在 JF1-H 访问的 states 上生成，learned action 一旦改变路线，后续 state distribution 即变化。高 offline preference accuracy 可能与 trajectory utility 无关，这与 JF2/HFR 已暴露的“可学习但无效用”风险同构。

因此 oracle 需要 sequential on-trajectory 版本，CostAware 需要分别报告 offline/on-policy regret，并预注册最多 1–2 轮 data aggregation。

### P0-10：局部可行不等于未来全局完成

route replay certificate 能证明当前 insertion 后的 capacity/TW/return 等局部约束，但无法保证未来未揭示订单仍有可行 completion。文档已统一把理论 claim 收窄为 action-level feasibility preservation；100% service、fallback 与终局 evaluator 保持硬 Gate。

## 9. 第二轮核对后的充分性判断

这些文档现在足以指导“如何把方法完善到可投稿证据链”，但**文档本身不等于论文证据已经充足**。真正 paper-ready 还取决于以下可执行产物：

1. C0 单位、状态、snapshot 与 trace-evaluator parity artifacts；
2. O0-D/O0-CC 的 common-continuation、label QC 与 100% service 正 headroom；
3. M0 frozen-MaskCO 表征探针；
4. M1 event mask、utility-aligned masked reconstruction 与 iterative refinement；
5. MaskCO 身份归因和冷链机制归因；
6. 多 seed、EDoD、场景与规模 robustness；
7. DEV/VAL 冻结后的 one-shot TEST。

换言之，v4 解决的是“动态冷链 MaskCO 主线怎样实现、每一步怎样证伪、失败后修哪一层”的规划完整性；核心正结果仍需按进度表生成。
