## 2. 先冻结 C0 合同

### 2.1 新建 `scripts/coldchain/coldchain_contract.py`

```python
class OperationalConfig:
```

必须记录 `schema_version` 和配置 hash。参数来源、单位、默认值与敏感性范围写入 manifest；没有来源或校准的值只能标 pilot。

主协议中的 `OperationalConfig` 不得运行时切换：车辆空载出发、客户处取货、单次返仓卸货。depot-to-customer delivery 必须使用新的 schema/version，不能只改注释。

### 2.2 新建 `scripts/coldchain/coldchain_state.py`

这是唯一热状态转移实现。推荐纯函数接口：

```python
@dataclass(frozen=True)
class CargoLotState:
    order_id: int
    quantity: float
    temp_class: int
    pickup_finish_time: float
    initial_quality: float
    quality_remaining: float

@dataclass
class VehicleColdChainState:
    compartment_temperature_c: np.ndarray
    zone_load: np.ndarray
    cargo_manifest: tuple[CargoLotState, ...]
    cumulative_energy_kwh: float
    finalized_quality_loss: float
    thermal_violation_duration_h: float
    door_open_count: int

def transition_segment(
    state,
    depart_time,
    arrival_time,
    service_finish,
    served_customer,
    active_zone_mask,
    contract,
) -> tuple[VehicleColdChainState, SegmentColdChainMetrics]:
    ...
```

规则：

- 主实验固定为同构多温舱、共享车辆总容量；每个订单只进入其 `temp_class` 对应舱室，所有舱室在 dispatch 时按合同预冷，并把冻结的预冷启动能耗计入该车；
- 车辆从 depot 空载出发；客户处货物在取货前由外部合规冷库保管，`service_finish` 时才把新订单以给定 `initial_quality` 加入 manifest 并增加载重；此前不得累计策略相关在途品质损失；
- 行驶、等待和本次开门先更新已有 manifest；新取订单以 `initial_quality` 加入；
- `return_arrival` 时记录每单返仓品质、统一卸货、清空 manifest 和载重，并关闭车辆；不允许 reload/multi-trip；
- 所有时间先转换为小时，再进入热模型；
- 功率用 kW，能量只按 kW×h 得到 kWh；J 转 kWh 必须除以 \(3.6\times10^6\)；
- 品质速率必须使用实际温度，而不是只按温区查常数；
- waiting、service/开门、行驶和返仓均计入；
- 函数不得原地修改输入 state；
- 主设置仅使用共享总容量；若未来增加独立舱容或异构车辆，必须升级 schema 并重新验证 route-slot 等价性，不能从 `temp_class` 暗推车辆能力。

### 2.4 新建 `scripts/evaluation/coldchain_evaluator.py`

接口：

```python
def evaluate_coldchain_trace(

    return {
        "distance_cost": ...,
        "quality_loss": ...,

        "thermal_violation_duration_h": ...,
```

## 3. C0 测试先于模型

新建 `scripts/tests/test_coldchain_contract.py`，至少覆盖：

1. dispatch 时 manifest 为空且总载重为零；
2. `service_finish` 才加入订单、增加正确总/分温区载重；
3. 品质计时严格从 `service_finish` 到 `return_arrival`；
4. 返仓卸货后 manifest/载重清零、车辆关闭且禁止再次派车；
5. 零时长状态不变；
6. kW×h→kWh 与 J→kWh 数值正确；
7. 更长暴露或更高风险温度不产生更低品质损失，并用换序算例验证高易腐订单后取可缩短 pickup 后暴露；
8. 开门事件不降低热负荷；
9. 返仓边计入距离、能耗和在途货物品质；
10. 同一 trace 的逐段累计与 evaluator 完全一致；
11. snapshot v3 round-trip 与 resumed manifest/thermal trace exact parity；
12. future 温度/类别扰动不改变当前动作输入；
13. 温区能力或容量不兼容 action 被 certificate 拒绝；
14. 所有原始分量与 `coldchain_cost` 可由 manifest 重算；
15. contract 校验参数来源标签、sensitivity 范围与 schema/hash。

C0 Gate 为上述 15/15 blocking tests 全部 PASS，并输出 `results/c0/coldchain_contract_tests.json`。

## 5. O0-D 与 O0-CC

新建 `scripts/evaluation/run_action_oracle.py`：

```text
--objective distance|coldchain
--trajectory baseline|sequential_oracle
--split val
--max_instances
--contract
--output_dir
```

输出逐事件和逐实例表。O0-D 验证原动作空间 distance headroom；O0-CC 使用完全相同的 candidate、transition、continuation 和预算，仅更换排序 outcome。

O0-CC Go：

- complete、TW、capacity、return 与温控硬约束均 100%；
- paired \(\Delta J_{CC}<0\)，95% CI 不跨 0；
- 改善不是少数异常实例贡献；
- \(D,Q,E\) 分项与权重敏感性可解释；
- candidate coverage 与运行时间可接受。

若 O0-CC No-Go，扩展顺序固定为：1–2 step lookahead → two-customer relocate/exchange → batch mask action。每扩一次 action schema 都重跑 oracle。

## 7. M1：DynMaskCO-CC 最小完整方法

新建：

- `scripts/models/dynmaskco_cc.py`
- `scripts/training/train_dynmaskco_cc.py`
- `scripts/simulation/dynmaskco_cc_replanner.py`

### 7.1 模型接口

```python
class DynMaskCOCC:
    def encode_visible_state(features, visible_mask, fleet_tokens, thermal_tokens): ...
    def build_event_mask(snapshot, replan_reason, risk_state): ...
    def score_masked_actions(encoded_state, mask, certified_candidates): ...
    def reconstruct(masked_plan, selected_action): ...
```

实现原则：

- 复用 DynamicColdChainModel/MaskCO encoder，不复制父项目源码；
- event mask 必须改变 decoder 输入或 action distribution；
- decoder 输出 utility-aligned action distribution，不预测 physical vehicle ID；
- masked reconstruction score 与冷链 utility residual 的组合方式写入 manifest；
- accepted action 通过 full-fleet/cold-chain certificate 后才能写回；
- 任何失败恢复完整 incumbent，不 silent drop。

### 7.2 训练

第一版只训练 action decoder/adapter：

$$
\mathcal L
=
\lambda_{list}\,\mathrm{KL}(p^*\Vert p_\theta)
+\lambda_{pair}\mathcal L_{pair}
+\lambda_{inv}\mathcal L_{future\text{-}inv}.
$$

主 Gate 正后才允许部分解冻 encoder，并以 `frozen → adapter → partial fine-tune` 顺序做单变量比较。

### 7.3 推理

```text
snapshot v3
→ event/risk mask
→ encode visible nodes + fleet/thermal tokens
→ enumerate certified action tokens
→ reconstruct best action
→ apply full fleet plan
→ guard + fallback
→ repeat at most K masked refinements
```

`K`、acceptance threshold、candidate top-k 与时间预算均在 dev/VAL 冻结。

## 8. M2 与数据闭环

如 M1 出现 offline 好、online 差，收集：

- first-divergence states；
- high predicted advantage/high oracle regret；
- fallback 或温控风险状态；
- 新 route composition 与高热负荷状态。

每轮重新使用同一 C0 contract 生成 labels。最多两轮，按 episode/state 平衡；禁止一直聚合到 VAL 变好。
