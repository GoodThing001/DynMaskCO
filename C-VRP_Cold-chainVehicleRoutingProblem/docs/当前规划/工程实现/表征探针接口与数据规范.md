# 表征探针接口与数据规范（M0）

> M0 只验证“在 strict-online 可见状态下，MaskCO 表征能否学习候选动作的冷链终局效用”，不是最终论文方法。本文冻结数据语义与防泄漏边界；当前不实现训练代码，不把 DEV-GATE、VAL 或 TEST 转为训练集。

## 1. 结论先行：现有 DEV-GATE 产物不能直接训练 M0

当前 `run_action_oracle.py` 的实例文件足以审计 DEV-GATE，但不是逐候选 teacher 数据集。实例 JSON 已保存 baseline/oracle 终局结果、local 事件均值和 sequential 选中动作日志；它没有保存每个候选的完整 action payload、candidate plan hash、终局 D/Q/E/J、hard vector 和拒绝原因。因此不得从 `oracle_log.jsonl` 反推未保存的候选，也不得把正式 DEV-GATE 数据重新 rollout 成训练集。

M0 需要在独立 TRAIN/DEV 数据上新增只读 teacher 导出过程，复用阶段 C 已验证的 snapshot、候选枚举、隔离 continuation、hard Gate 与 rollout 语义，但输出单独版本化的数据合同。任何实现都应先在 DEV-PROTO 做格式与 parity 回归，再生成正式训练数据。

## 2. 样本与三级索引

一个基础样本定义为同一决策上下文中的一个候选动作：

\[
(S_{m,e}, i, a)\longrightarrow
(Y_a,\Delta_a,H_a,C_a),
\]

其中 \(m\) 是基础实例，\(e\) 是事件，\(i\) 是当前客户，\(S_{m,e}\) 是可恢复快照，\(a\) 是候选动作，\(Y_a=(D_a,Q_a,E_a,J_{CC,a})\) 是共同 continuation 的终局结果，\(\Delta_a=J_{CC,a}-J_{CC,\mathrm{keep}}\)，\(H_a\) 是终局 hard vector，\(C_a\) 是动作级 certificate。

最小索引必须同时保留：

- 实例层：`dataset_role / cell / scene_instance_id / instance_seed / inst_idx`；
- 事件层：`event_id / clock / state_hash`；
- 客户层：`customer / customer_rank / context_id`；
- 动作层：`action_id / action_hash / candidate_plan_hash`。

`context_id` 建议由 `(dataset_hash, inst_idx, event_id, state_hash, customer)` 的规范序列化计算。所有事件和候选必须能追溯到一个基础实例，禁止把候选行号当作独立样本身份。

## 3. Snapshot 输入合同

权威快照是 `recourse_snapshot_v3_cc`。M0 输入可以由快照派生，但原始 teacher 记录必须绑定完整 `state_hash`。快照当前包含以下字段族：

| 字段族 | 关键字段 | M0 用途 |
|---|---|---|
| 身份与时钟 | `schema_version, instance_id, event_id, clock, reveal_idx, replan_count` | 事件定位与顺序 |
| 可见性与服务 | `served_mask, visible_mask, customer_universe` | non-anticipatory mask 与 decision pool |
| 车辆状态 | `vehicle_status, vehicle_node, vehicle_ready, vehicle_load` | fleet token |
| committed 状态 | `committed_next/arrive/finish` | 冻结 leg，不可作为 mutable 动作目标 |
| 可变计划 | `needs_replan, replan_reason, mutable_suffix, mutable_suffix_len` | 计划 token 与 mutable mask |
| 历史轨迹 | `served_route, dispatch_time, return_finish, services_*` | 已执行前缀与 trace 状态 |
| continuation | `force_suffix, replanner_state` | 精确恢复与 deferred 隔离 |
| 冷链状态 | `vehicle_coldchain_state, services_coldchain, trace_*` | 温度、manifest、品质与能耗状态 |
| 完整性 | `coldchain_contract_hash, state_hash` | 合同与状态身份 |

训练张量只允许使用当前时刻可见字段；完整快照可以为恢复和审计保存，但进入模型前必须经过显式 feature allow-list。模型侧的 `visible_mask`、`mutable_vehicle_mask` 和 `decision_customer_mask` 必须分开，不能用一个 mask 混合三种语义。

## 4. 模型可见特征与禁止特征

允许的订单特征包括当前已经揭示订单的坐标、需求、时间窗、服务时间、温区和初始品质；坐标统计必须由 visible-only normalization 计算。允许的车队特征包括各车 anchor 节点、ready/committed 时间、当前载重、状态、已经冻结的 committed leg、可变 suffix，以及当前舱温、zone load、manifest 汇总和累计冷链状态。动作特征包括客户、slot 类型与 anchor、插入位置、predecessor、successor、是否 incumbent 及动作 certificate。

以下信息只能作为标签或审计数据，绝不能进入模型输入：

- `reveal_time > clock` 的订单坐标、需求、时间窗、温区和真实 reveal 序列；
- 候选 rollout 产生的终局 `D/Q/E/J_CC`、hard vector、reject reason 和 selected 标记；
- 后续事件状态、未来最优路由、oracle 选择以及同一实例的其他未来快照；
- 用全部节点计算的坐标归一化统计；
- 数据角色、文件名或 seed 的可预测编码，如果它们会泄露场景/标签。

Teacher 导出时应同时存储 `feature_schema_version` 和最终进入模型的 feature mask 摘要，以便执行 future-invariance 测试。

## 5. 动作、KEEP 与 DEFER

普通动作使用 `FleetAction` 的规范字段：

```text
customer, slot.kind, slot.anchor, position,
predecessor, successor, incumbent
```

`action_id` 沿用当前确定性字符串；`action_hash` 应对上述结构化 payload 的规范 JSON 计算 SHA-256，不能只散列展示字符串。`candidate_plan_hash` 直接使用候选应用后的 full-fleet `plan_hash`。`allowed_vehicle_ids`、源车辆、最终匹配的 physical vehicle 以及 non-mutable 车辆前后 plan hash 都要保存，用于证明动作 scope 没有越界。

`KEEP` 和 `DEFER` 是两个不同的伪动作。客户已经在 incumbent suffix 时保持计划记 `__KEEP__`；客户尚未分配时保持遗漏状态记 `__DEFER__`。二者都以同一 `keep_outcome` 为比较基准，但必须保留 `incumbent_exists`，不能把 DEFER 伪装成已分配客户的 no-op。训练时每个 `(state, customer)` 上至少包含一个基准伪动作；若导出器无法构造或验证它，应拒绝该上下文。

## 6. 候选 certificate、终局标签与 Gate

每个候选应保存动作级 certificate：

```text
feasible, reason, incremental_distance,
tw_slack, cap_slack, return_slack,
temperature_compatible, total_capacity_slack,
manifest_consistent, coldchain_reject_reason
```

当前 certificate 中 `projected_energy_kwh / projected_quality_loss / projected_thermal_margin` 可能为 `null`；它们不是终局标签，也不得以 0 填补。对 certificate 不可行的候选可以保存为“枚举负例”，但不得执行 rollout；对 certificate 可行的候选才保存 rollout 终局标签。

终局记录必须包含 baseline/KEEP/candidate 三类 outcome，并完整保留：

- `distance_km, quality_loss, energy_kwh, coldchain_cost`；
- `complete, n_unserved, n_duplicate, capacity_feasible, tw_feasible, depot_return_feasible`；
- `all_orders_picked, all_cargo_delivered_to_depot, terminal_manifests_empty, all_enabled_vehicles_returned`；
- `temperature_hard_feasible, distance_accounting_consistent, trace_accounting_consistent`；
- `ownership_violations, terminal_unresolved, contract_hash, coldchain_schema_version`。

缺字段、NaN/Inf、非整数计数、accounting 失败或 ownership 失败标记为 `PROTOCOL_ERROR`，不得进入损失函数。协议有效但 service 不完整的候选标记为 `SERVICE_FAIL`，可作为可行性辅助任务的负例，但不得参加 cost preference 排名。只有 `service_ok=true` 的候选才能形成 \(J_{CC}\) 排序标签。

建议同时输出以下派生标签：

```text
delta_vs_keep = J_candidate - J_keep
strictly_improving = delta_vs_keep < -tau(keep_cost)
rank_within_context = rank by (J_candidate, action_id)
selected_by_teacher = candidate equals stable best improving action
```

## 7. 当前产物与未来 teacher 的字段对账

现有回归实例 `results/o0cc/v4_archive_wire_regression/.../instances/inst_0.json` 的实际结构如下。该表同时界定哪些字段已经存在、哪些仍需 teacher 导出器新增。

| 层级 | 当前已有 | 当前缺口/处理 |
|---|---|---|
| 实例 | `inst_idx, code_sha256, runtime, error` | 新增 dataset/cell/seed/teacher schema 身份 |
| 终局 | `baseline, oracle` 的完整 D/Q/E/J 与 hard/repair 字段 | teacher 需另存 KEEP 与每个候选 outcome |
| sequential 日志 | `seq, event_id, state_hash, customer, keep_cost, selected_cost, selected_delta, selected_action` | 只保存最终选择；没有所有候选 action/outcome |
| coverage | `num_candidates, num_feasible, num_rolled_out, num_hard_pass, reject_reasons, n_rollouts` | 是计数，不可还原候选级训练行 |
| local | `event_deltas, records, base_cost`；record 有 `event_id, n_customers, n_customer_deltas, mean_customer_delta, keep_cost` | 仅事件均值，没有 customer/action 明细 |
| snapshot | 运行时存在并用于 rollout | 当前实例 JSON 不持久化；M0 teacher 必须保存或以内容寻址方式引用 |
| action | `selected_action` 字符串 | 新增结构化 payload、action hash、plan hash、scope |

因此，DEV-GATE 的 `oracle_log.jsonl` 只能作为协议与选择轨迹证据，不能被宣称为 M0 teacher 数据。

## 8. 存储布局与原子发布

建议 teacher 数据采用“上下文表 + 候选表 + manifest”三层，而不是在每个候选重复整份快照：

```text
teacher_dataset/
├── manifest.json
├── contexts/
│   └── <context_id>.npz或json
├── candidates/
│   └── part-*.parquet或jsonl
└── qc/
    ├── gate_summary.json
    └── parity_summary.json
```

`manifest.json` 至少绑定数据文件 hash、代码/合同/profile hash、baseline 配置、snapshot/feature/action/label schema 版本、实例集合和生成命令。发布应沿用 DEV-GATE 的临时文件、刷盘、原子 rename 与 COMPLETE marker 机制；未完成分片不得被训练入口读取。

## 9. 分组、损失与统计单位

同一 `(state_hash, customer)` 的候选属于一个 decision context。Pairwise/listwise preference 只能在同一 context 内比较，训练采样先抽基础实例，再抽事件、客户和候选，避免候选数量多的事件获得不成比例的权重。候选级准确率只能作诊断；正式 M0 评估至少报告 context-level top-1、pairwise ranking、预测动作的 normalized regret，以及用预测动作 sequential rollout 后的实例级 \(J_{CC}\)。

Teacher 的 `selected_by_teacher` 不应成为唯一标签。主标签保留连续的 `delta_vs_keep` 或同 context 的相对效用；否则模型只能模仿在固定 tie-break 下的单一动作，无法利用近似等价候选。

## 10. 数据划分与防泄漏

Train/dev/validation/test 必须按基础 `instance_seed` 划分；同一实例的所有事件、客户、候选和派生增强只能出现在一个 split。DEV-CAL、DEV-PROTO、DEV-GATE、O0-CC VAL 和 TEST 均不进入 M0 训练，其中 DEV-PROTO 只允许用于导出器的格式测试，DEV-GATE 只用于已经冻结的动作空间路线判定。

正式生成训练数据前需要另建独立 `TRAIN-TEACHER` 与 `DEV-TEACHER` manifest。任何 on-policy aggregation 也按基础实例归属原 split，最多执行预注册的 1–2 轮，且不得把 VAL/TEST 轨迹回流训练。

## 11. M0 公平比较与准入条件

M0 比较 frozen pretrained causal MaskCO encoder、random encoder、generic encoder、feature-only head 和 label shuffle。各变体必须使用相同可见特征、候选集、数据 split、损失、优化预算和实例级统计口径；只有编码器来源或指定消融不同。

M0 的 `GO` 只表示存在可学习的动作效用信号，至少要求真实 MaskCO 表征在独立 DEV-TEACHER 上优于 label shuffle，并在实例级 sequential 验证中不劣于 feature-only/generic 对照。它不等于最终 DynMaskCO-CC 已成立，也不授权读取 TEST。启动 M0 以前还必须满足：正式 O0-CC 路线已确定、teacher schema 和 QC 测试冻结、独立训练数据 manifest 已建立。
