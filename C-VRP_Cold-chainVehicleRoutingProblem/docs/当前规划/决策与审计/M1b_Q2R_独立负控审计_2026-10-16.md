## 1. 任务 A：Ω11 时间可行性负控

对照物：`action_contract.certify_route:142-203`（真实时间窗语义）
与 `m1b_return_feasibility.certify_return_feasibility`。

**逐项对照结论**：`certify_route` 的时间推进是
`arrive = t + travel` → **`start = max(arrive, tw_start)`** → `t = start + service_time`
（`:184-196`），最后 `return_time = t + travel(cur,0)`、`return_slack = tw_end[0] − return_time`
（`:198-201`）。
Ω11 的时间推进是 `t = max(ready_time, clock)` → `t += travel` → `t += service_time`
（`m1b_return_feasibility.py` else-分支），**没有 `tw_start` 等待项**，且服务时长取自
**模块级缓存**，缺省 **0.0**。

| 例 | INPUT（最小可复现） | EXPECTED | ACTUAL | 分类 |
|---|---|---|---|---|
| **A1** | `tw_start[5]=20.0`, `T_end=19.0`, travel 1.0/leg, service 0.0 | `OMEGA11_RETURN_DEADLINE_EXCEEDED`（真实返仓 **21.0** > 19.0+1e-6） | **`OMEGA11_OK`**，Ω11 报返仓 **2.0**；同一输入 `certify_route` 判 `feasible=False, reason='return', return_slack=-2.0` | **`FALSE_PASS`** |
| **A2** | `service_time[5]=2.0`，**缓存为空**，`T_end=8.0` | 服务时长不可得 ⇒ 应拒绝，或至少不得静默取 0 | `OMEGA11_OK`（此例 `T_end` 宽裕，两法同结论） | **`NOT_ESTABLISHED`** |
| **A2b** | 同上但 `T_end=3.5` | 拒绝；真实返仓 **4.0** > 3.5+1e-6 | **`OMEGA11_OK`**，Ω11 报 **2.0**；`certify_route` 判 `False/'return'` | **`FALSE_PASS`** |
| **A3** | 实例1 注册 `service[5]=5.0` → 实例2 注册 `service[5]=0.5` | 每次运行用**本实例**服务时长 | 两次运行返仓时刻**不同**（缓存被覆盖后生效）；**无实例身份绑定**，忘记重新注册即复用上一实例 | **`NOT_ESTABLISHED`** |
| **A4** | `status='committed'`, `committed_finish=2.0`, `committed_next=3`, **`mutable_suffix=[6,0]`**, `T_end=6.0` | 须同时计入 committed 段**与**后续已接受任务（真实返仓 **4.0**） | Ω11 报 **3.0**，`basis='committed_finish + travel(committed_next -> depot)'` —— **后缀被完全忽略** | **`NOT_ESTABLISHED`** |
| **A4b** | 同上但 `committed_finish=4.0`, `T_end=5.0` | 拒绝；真实返仓 **6.0** > 5.0 | **`OMEGA11_OK`**，Ω11 报 **5.0** | **`FALSE_PASS`** |
| **A5** | 车 `mutable_suffix=[]`（WAIT），**候选计划为 `[7,0]`**，`clock=1.0`, `T_end=24.0` | 必须为**它正在认证的那个候选计划**计时：20.0+1+1+1 = **23.0** ≤ 24.0 | Ω11 报 **2.0**（"现在即返仓"），`basis` 自述 WAIT 判"现在返仓" | **`NOT_ESTABLISHED`** |
| **A6** | `status='closed'`, `return_finish=30.0`, `T_end=24.0` | 已closed车的**历史**返仓越界应可独立审计 | closed 分支 `pending=False`，**完全跳过** `return_finish` 与截止比较 | **`NOT_ESTABLISHED`** |

### A 组根因（逐条给源码位置）

- **A1 根因**：`m1b_return_feasibility.py` 的 `else` 分支以
  `t = float(max(v.ready_time, clock))` 起步，**从不应用 `start = max(arrive, tw_start)`**，
  因此**遗漏等待时间**——而等待正是 `action_contract.py:187` 显式计入的量。
- **A2/A2b 根因**：`_service_time(node, snap)` 为
  `float(_SERVICE_TIME_CACHE.get(int(node), 0.0))` —— **缺省 0.0 且无出处校验**；
  真实服务时长来自 `env.service_time[inst_idx, j]`（`action_contract.py:196`）。
  **零缺省只会低估时长 ⇒ 只会产生乐观（假通过）判定。**
- **A3 根因**：`_SERVICE_TIME_CACHE` 是**模块级全局字典**、仅按 node 索引，
  无实例/状态身份；`register_service_times` 是"覆盖式"注册，**忘记调用即静默复用**上一实例。
- **A4/A4b 根因**：`elif v.status == "committed"` 分支**只**计算
  `committed_finish + travel(committed_next -> depot)`，**从不检视 `plan.suffix` / `mutable_suffix`**，
  故同一车上**已接受的后续任务被漏计**。
- **A5 根因**：WAIT 路径仅在候选后缀为空时进入并判"现在返仓"；
  当**候选计划本身继续去客户 7**（`plan(0, 20.0, [7,0])`）时，
  该分支报告的 2.0 与候选计划真实的 23.0 **描述的是两个不同的计划**——
  门认证的与自己计时的不是同一个对象。
- **A6 根因**：`if v.status == "closed"` 直接 `pending = False; continue`，
  `return_finish` 从不参与比较，历史越界对该门不可见。

### B1 根因（**最严重**）

1. `m1b_q2_certifier.py:_default_lot_provider` **只**采集"**有 plan 的车**之 **cargo_manifest** 内的 lot"。
   manifest 为空 ⇒ 返回**空集**。
2. `m1b_quality_certificate.check_omega10_initialization` 在 `checked == 0` 时返回
   **`ok=True`** 且 `verdict=OMEGA10_NO_RELEVANT_LOTS`。
3. 编排器把 `ok=True` 直接当作通过 ⇒ 复合 `True`。

⇒ **"无可检对象"与"已检验且合格"在编排层不可区分。**
B4 证明**比较逻辑本身是对的**；洞在**覆盖层**（谁被送去比较）。

**对原 Q2 报告的一处限定（不改写，仅补充）**：报告 §2 描述 Ω10
"只读 manifest 载货、候选涉及的已揭示订单、已承诺可见订单"——
前半句是**默认 provider 的实际行为**，但**后半句在本实现中并未落实**：
**没有任何代码读取"候选计划涉及的已揭示订单"的初值**。B1 即该缺口的最小反例。

**与用户约束的直接对应**：用户明确要求
"任何属于当前候选或已接受承诺的鱼，若初值尚未验证，不得被视作 Ω10 已建立"。
B1 表明**当前实现对"当前候选"不满足该要求**。

### C1（**可升级路径，须单列**）

`m1b_thermal_gate.replay_thermal_envelope` 在**满足采样包络**时返回
`THERMAL_HARD_OK`，而"连续时间未验证"这一限定**只写在每车 `detail.envelope` 内部**
（`continuous_time_hard_constraint = NOT_VERIFIED_CONTINUOUSLY`）。
`m1b_q2_certifier` 把顶层 `THERMAL_HARD_OK` 置 `True` 并直接进入
`composite_pass = bool(all_gates and q_ok and t_ok)`。

⇒ **只读 `composite_pass` 或顶层 `THERMAL_HARD_OK` 的下游消费者，无法区分
"采样合规"与"连续时间合规"**。这是**升级路径**（PROMOTION_PATH_EXISTS），不是数据缺陷，
但它使一个**采样级**结论在接口上**可被读成连续级**保证。

### C4：`composite_pass=True` 究竟证明了什么（实测）

**证明了**（对**本次传入的**输入）：
1. 合同为 v2 且身份字段与 `contract_hash` 齐备；
2. 快照隔离、无别名、认证前后状态身份一致；
3. **所检查的** lot 初值与合同一致（`1e-9` 内）；
4. **采样**返仓时刻在 `T_end + 1e-6` 内；
5. **采样**温度包络在 `hard_temperature_bounds_c` 内（且该车既有累计违规为 0）；
6. 解析品质下界高于阈值。

**没有证明**：
1. M1-a 的 legality / repair / partition / route feasibility；
2. 真实 C0 能源预算（`certify_plan`）；
3. **未揭示订单**或**仅出现在候选计划中**的鱼的初值（**B1**）；
4. **连续时间**温度硬约束（**C1**）；
5. 服务时长与时间窗等待被正确计入（**A1/A2b**）；
6. committed 车后续任务的返仓可行性（**A4b**）；
7. 与安装事务共享的状态身份（C2）；
8. 任何生产可安装性。

## 4. 对生产可安装性的影响

**结论：C（生产可安装性）在 Q2 报告中标注的"未建立"，经本轮审计进一步收紧。**

⇒ 即便将来把该认证器接到 commit 路径，**上述四类轨迹仍会被放行**。
**生产可安装性状态不变（未建立），但"仅差接线"这一读法不成立。**

## 6. M1-b/Q3 是否具备开始资格冻结的结论

1. **Q3 的资格冻结以 Ω10/Ω11 为前置**，而两者各有**可复现的假通过**（A1、A2b、A4b、B1）——

4. 生产可安装性并非"仅差接线"（§4）；
5. C2/C3 表明 M1-b 复合门与 M1-a 四项检查、真实 `certify_plan`、安装事务身份**均未接合**，
   Q3 需要先明确"资格"到底覆盖哪一组门。

**建议的下一步（需另行授权）**：先执行 §5 的 **F-A1/A2/A3/A4/A5/A6 + F-B1 + F-C1** 修复，
