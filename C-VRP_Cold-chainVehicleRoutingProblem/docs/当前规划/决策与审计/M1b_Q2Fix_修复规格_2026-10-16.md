## 3. 新版认证语义

### 3.1 统一时间重放（Ω11 与温度门**共用同一实现**，消除口径不一致）

```
depart      = max(anchor_time, clock)          # 与候选绑定的可信起点
arrival     = depart + travel(u, v)
service_start  = max(arrival, tw_start[v])     # 与 certify_route:187 一致
service_finish = service_start + service_time[v]
return_arrival = final_service_finish + travel(last, depot)
```

**硬要求**

1. 起点必须与候选绑定：校验 `anchor_time`、`anchor_node`、`anchor_load` 与 `clock`；
   不一致即拒绝（`OMEGA11_ANCHOR_MISMATCH`）。
2. `tw_start` 与 `service_time` **必须由调用方按实例提供**；缺失 ⇒ **拒绝**
   （`OMEGA11_TIME_INPUT_UNAVAILABLE`）。**禁止静默 0**。**允许**合法的真实 0 值
   （以"键存在"区分"值为 0"与"未提供"）。
3. **删除** `_SERVICE_TIME_CACHE` 与 `register_service_times`；时间输入随快照传入并携带身份。
4. committed 车辆：先继承真实在途段（`committed_next` / `committed_finish`），
   **再继续重放**其后已接受任务与候选后缀。
5. WAIT：一律以**被认证候选**为准；若候选为空且车不在库，按"最早可返仓"计算，
   **并在收据写明所用对象身份与 depart 选择**。
6. closed 车辆：通过**传入的可信历史**（trace/持久化记录）核验；
   若历史中 `return_finish` 缺失，**不得**据此判通过（`OMEGA11_CLOSED_HISTORY_MISSING`），
   但也**不得**仅因当前字段为空而误拒。
7. 收据写入：计划身份、时间输入身份、逐车 `return_arrival`、失败原因。
8. 与 `certify_route` **独立对拍**：同一输入下两者对 return 的可行性判定必须一致
   （允许 1e-9 容差）；不一致即拒绝（`OMEGA11_CERTIFY_ROUTE_DISAGREEMENT`）。

### 3.2 覆盖率认证（Ω10）

独立构造应检集合 `E` 与实际验证集合 `C`：

- `E_loaded`：已装载鱼类订单（manifest）
- `E_committed`：已接受未完成的鱼类承诺
- `E_candidate`：候选计划中**已揭示**的鱼类订单
- `E = E_loaded ∪ E_committed ∪ E_candidate`

**机械对照**：`C` 必须 ⊇ `E`；`C \ E`（多余身份）⇒ 拒绝（`OMEGA10_COVERAGE_EXTRA`）；
`E \ C`（缺漏）⇒ 拒绝（`OMEGA10_COVERAGE_INCOMPLETE`）；身份重复冲突 ⇒ 拒绝
（`OMEGA10_COVERAGE_IDENTITY_CONFLICT`）。

| 情形 | 判据 |
|---|---|
| `E` 非空 | **必须**完整验证每件鱼的实际/可信待入库初值 |
| `E` 为空**且来源完备** | 允许 `OMEGA10_NO_FISH_IN_SCOPE`，**但不得**声称验证了实际存在的鱼 |
| 候选有鱼但初值未知 | **拒绝**（`OMEGA10_CANDIDATE_VALUE_UNKNOWN`） |
| 来源不可识别 | **拒绝**（`OMEGA10_SOURCE_UNIDENTIFIABLE`） |

**结构性可见性限制**：`initial_quality_by_node` / `temp_class_of` / `quantity_of`
**不得**为"无来源验证的全节点真值表/任意回调"。改为**具名、带身份**的只读提供者：
必须声明其**来源身份**与**覆盖的节点集合**，且**仅可查询已揭示节点**；
查询未揭示节点返回 `PermissionError` 语义的拒绝。

**边界不变量**：`check_boundary_initial_value` 在 reveal / accept / pickup 三处维持同一不变量。

### 3.3 温度认证等级（§五）

| 状态 | 含义 |
|---|---|
| `THERMAL_SAMPLED_OK` | 采样包络（段端点 + 每次门事件后）在 `hard_temperature_bounds_c` 内 |
| `THERMAL_CONTINUOUS_OK` | 段内连续时间极值已**严格证明**在界内 |
| `THERMAL_CONTINUOUS_NOT_ESTABLISHED` | 未建立（本轮默认） |

**复合规则**：`composite_pass` **要求** `THERMAL_CONTINUOUS_OK == True`。
本轮不实现解析极值证明 ⇒ **复合恒 fail-closed**（`THERMAL_CONTINUOUS_NOT_ESTABLISHED`
使复合拒绝）。采样级结果**保留**为独立工程诊断，**不得**命名为完整可安装证书。

热重放的时间推进**必须**使用 §3.1 的统一实现（含等待与服务时长）。

## 4. 失败与未知状态的处理

**一律 fail-closed**：`None` / `NaN` / `±inf` / 类型不符 / 状态缺失 / 来源不可识别 /
身份冲突 / 覆盖不完备 / 与 `certify_route` 不一致 ⇒ **拒绝**。**未知不得等于通过。**

## 7. 勘误：Q2-R 报告 A5 记录与 JSON 不一致（**以 JSON 为准**）

**事实**：`results/_m1b_q2/negative_controls_q2r.json` 的 A5 记录为
`omega11_return_arrival = 4.0`、`n_suffix_stops = 1`；
而 `M1b_Q2R_独立负控审计_2026-10-16.md` §1 表中 A5 的 ACTUAL 写作 **2.0**。

**实测复现**（本轮）：冻结计划 `[7, 0]`、`ready_time=1.0`、`clock=1.0`、每段 1.0、
`service[7]=1.0` ⇒ 重放推进 `1+1+1+1 = 4.0`，与 JSON 一致。

**结论**：**JSON 正确，报告文本错误。** 我错误地把共享的 pending 车 `basis` 文字里的
"return now" 读成了数值，而未核对 JSON。
**因此 A5 的原始描述（"报 2.0"）不成立**：门**确实**读取了候选计划的后缀。

**A5 仍然成立的较窄事实**：
`basis` 字符串自带 "return now (earliest possible)"，但实际推进起点为
`max(ready_time, clock)`，二者**不一致**；且 depart 的选取**不受不变量约束**。
当 `anchor_time < clock` 时（WAIT 后继续等待的解），以 `clock` 起算可能**低估**等待代价。
⇒ A5 的类别应为 **`BASIS_LABEL_MISMATCH_AND_DEPART_UNGUARDED`**，
而非"报 2.0 的假通过"。**原报告与 JSON 均保留不改**；本勘误单列。
