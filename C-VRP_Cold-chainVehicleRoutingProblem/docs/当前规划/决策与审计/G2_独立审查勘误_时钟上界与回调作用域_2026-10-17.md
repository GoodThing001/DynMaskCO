## 2. A-1：`_force_return_all` **推翻** "`T_max` 覆盖全部时钟"

### 2.1 机制（源码路径）

```
strict_online_env.py:506  if next_clock > horizon - 1e-6:
strict_online_env.py:507      self._force_return_all(inst_idx, clock, ...)
strict_online_env.py:658  def _force_return_all(self, inst_idx, clock, ...):
strict_online_env.py:661      self._commit(inst_idx, clock, v, traces, 0)   # 返仓 leg
strict_online_env.py:273          v.return_finish = depart + self._travel(inst_idx, v.current_node, 0)
strict_online_env.py:664      self._advance_fleet(inst_idx, finish, [v], ...)
strict_online_env.py:304          self._advance_coldchain_to(v, clock)      # clock = finish
```

`depart ≤ clock ≤ horizon`，但 `finish = depart + travel(current, 0)` **可以超过 horizon**。
于是**最后一个进入温度推进函数的时钟**是 `horizon + 最多一个返仓 leg`，不是 `horizon`。

### 2.2 实测反例（E-01，2 节点合成 episode）

| 量 | 值 |
|---|---|
| 构造 | depot + 1 客户，客户距 depot **0.9**；`tw_start = 23.5`、`service_time = 0.4` |
| 事件时钟（`snapshot_hook` 记录） | `[0.0, 23.899999618530273]` |
| `_advance_coldchain_to` 收到的**最大**时钟 | **`24.799999594688416`** |
| 超出 horizon | **`+0.7999995946884155`** |
| 监视器计数 | 该车 2 次推进 |

**这是用本仓库自己的代码路径得到的反例，不是论证。** 原报告"每个时钟 ≤ `T_max`"的说法
（以及旧审计模块的 `L1-6` 前置条件）**不成立**。

## 3. A-2/A-3：修正后的时间误差预算——区分**最大时间戳**与**事件循环 horizon**

### 3.1 修正

```
T_clock_sup = horizon + travel_bound
slack       = [1e-9 + ulp_c(T_clock_sup)/2] + [n_max · ulp_c(T_clock_sup)/2]     (hpu = 1.0)
```

`travel_bound` 的来源必须**登记**，本模块只接受三种（`TRAVEL_BOUND_SOURCES`）：

| 来源 | 可见性 | 依据 |
|---|---|---|
| `coordinate_box_diagonal` = `√2 / tw_speed` | ONLINE-DECISION | 坐标落在单位方块内是**域级不变量**（实测 `[0.0201, 0.9798]`，实测最大成对距离 1.276295） |
| `served_leg_max` | ONLINE-DECISION | 返仓 leg 的起点是**车辆实地到达过**的节点，其距离此时已披露 |
| `caller_declared_with_witness` | CERTIFIER-PROOF | 申报值只在与实测时钟相符期间成立 |

### 3.2 本域数值不变，但**推导**换了（E-02/E-07）

| 场景 | `ulp` 基准 | 结果 |
|---|---|---|
| 登记域：`24.0` vs `24 + √2 = 25.4142…` | 同属 `[16,32)` binade | **slack 完全相同**：`1.0710684844307253e-09` h |
| 跨 binade：`horizon = 1048575.5`、`travel = 1.0` ⇒ `T_clock_sup = 1048576.5 ≥ 2^20` | ulp **恰翻倍** | slack 由 `2.3297721e-06` 变 **`4.6585442e-06`**（比值 1.99957） |

**读法**：
- 在登记域，**没有任何数值结论被撤回**（E-07 给出两个精确有理数的相等）；
- 但"以 horizon 为 ulp 基准"这个**推导**本身是错的，它在别的时域会**低估一倍**；
- 因此**采纳**修正后的基准，并把"数值未变"登记为**巧合**（同 binade），不是正确性依据。

### 3.3 `n_max = 20003`：只保留 `max_iter` 单界（E-03）

| 项 | 值 |
|---|---|
| 采用的上界 | `1 + 2·max_iter + 2 = **20003**`，`n_iter ≤ max_iter`（源码显式循环上限） |
| 撤销的收紧 | `n_iter ≤ 1 + floor(T_max/eps_event)` → `NOT_ADOPTED`；若采用会得 `n = 2005` |
| 撤销理由 | 该式需要"每次迭代时钟前进 > `eps_event`"，**源码无此断言**，只有一次合成观测 |

**这正是审查意见要求的处理**：先只用源码中显式的结构上界，不依赖未经证明的更紧公式。

## 5. A-4：安装门是 **fail-closed** —— 更正我上一轮的措辞（E-05）

源码事实（`d3_geo_adapter.py:721-725`）：

```python
if INSTALL_REQUIRES_CERTIFICATION and kwargs.get('certify_fn') is None:
    return ledger.finish(failure_reason='no_certifier', ..., refused_before_sampling=True)
```

`ledger.finish` 在 `failure_reason is not None` 时**直接返回 False**（`:640`），安装回调**从不被调用**。
实测（E-05，真实调用一次拒绝路径）：

| 量 | 实测 |
|---|---|
| `run_repair_transaction(certify_fn=None)` 返回 | `False` |
| `n_installs` | **0** |
| `n_pre_sampling_refusals` | **1** |
| `installed_plans` | **`[]`** |
| 安装回调被调用次数 | **0** |
| ledger 事件 | `{'action': 'refuse', 'reason': 'no_certifier', 'refused_before_sampling': True, ...}` |

**三句必须分开写的话**：

1. **【事实】** M1-b 认证器**没有生产接入**，认证链未闭合；
2. **【事实】** `run_repair_transaction()` 对缺认证的路径 **fail-closed**（拒绝安装，零安装）；
3. **【推断】** 因此主要缺口是"**无法形成可用的认证与安装闭环**"，
   **不是**"`None` 导致未认证计划被安装"。

**我上一轮写"`certify_fn=None` 跳过认证（既有 G0 A-2 缺口，未变）"是不精确的**：
该描述只对 `stepwise_sample_d3` 的**直调**路径成立（两臂协议 `d3_l1_two_arm_protocol.py:338`
就是直调，故 V3 记 `NOT_RUN`），而**安装事务**是 fail-closed。此处更正，原报告不改写。
