## 2. 独立复核发现

### 2.1 异议一：Ω 不能保证入库初值 = 合同 `initial_value[c]`（**成立**）

**源码链（逐项核实）**

| # | 事实 | 行号 |
|---|---|---|
| 1 | `StrictOnlineEnv` 直接取 dataset 的 `initial_quality`；**缺失时默认全 1** | `strict_online_env.py:159-161` |
| 2 | 该数组原样传入 `transition_segment`，**无任何"是否等于合同初值"的校验** | `:328` |
| 3 | v2 pickup 分支**只要求** `initial_quality > 0`，随后直接写入 `CargoLotState` | `coldchain_state.py:248-252`、`:270-278` |
| 4 | 合同 `QualityConfigV2.initial_value` 与 `validate` 中的 `initial_value[i] > 0` | `coldchain_contract.py:581`、`:594-595` |
| 5 | v2 语义转换器 `add_v2_initial_quality`（把 `temp_class==c` 的置为 `initial_value[c]`）**只是一个普通函数**，由调用方决定是否使用 | `coldchain_evaluator_a1.py:20-33` |

**⇒ 结论**：`QualityConfigV2.initial_value[c] = 9.0` **不构成**对实际入库初值的运行时保证。
Ω1–Ω9 中**没有任何一条**要求该等式。

**实测（R1/R5）**：`transition_segment` 对温区 1 接受 `initial_quality ∈ {1.0, 9.0, 0.5, 1e-6, 100.0}`；
仅 `0.0` 被拒（`ValueError: initial_quality must be positive (v2 absolute score)`）。

**覆盖面（事实）**：`add_v2_initial_quality` 在仓库中出现于 **60+ 处**（正式入口
`run_a1_step2_gate.py:287`、`run_a1_external_accept.py:344`、`run_a1_downstream_ablation.py:375`、
`run_exp_a1_compare.py:121`、`run_a1_step3_compare.py:298`、以及 I3 系列与大量 test/diag）。
**⇒ 正式协议实践上确实做了转换**；但这是**调用约定**，不是 Ω 的**约束**。

### 2.2 异议二：Ω5 的 `1e-6` 容差未进入下界（**成立**）

Ω5 写作 `t_ret ≤ T_end + 1e-6`（`action_contract.py:200-202`、`coldchain_evaluator_a1.py:84`），
但原证明第 3 步直接用了 `D(i) ≤ T_end − 0`。**严格地，该步不成立**，应为：

```
D(i) ≤ (T_end + 1e-6) − t_min,   t_min := 已验证的最早 pickup_finish（不可验证时取 0）
H_max = (T_end + 1e-6 − t_min) · hours_per_time_unit
```

**数值影响（实测）**：本次 `T_end = 24.0`、`t_min = 0`、`hours_per_time_unit = 1.0`：

| 温区 | 原 `Q_LB`（24.0 h） | 修正后 `Q_LB`（24.000001 h） | 差 |
|---|---|---|---|
| 1 冷藏鱼 | 8.548080 | **8.54807998117** | **−1.883e-8** |
| 2 冷冻鱼 | 8.993328 | **8.99332799972** | **−2.78e-10** |

⇒ **对当前 24 h 合同的可售判定无实质影响**，但**证明必须与执行器一致**——用户此点判断准确。

**`t_min = 0` 的依据（源码事实，非假设）**：环境在 `clock = 0.0` 起步
（`strict_online_env.py:115`），时钟只由事件推进（`:510 clock = next_clock`，
`next_clock` 取自揭示/完成时刻，均 `≥ 0`）；实测三个 m0_scale 文件的 `min(tw_start) = 0.0`、
`tw_start[0] = 0.0`。**注意**：`tw_start[0]` 并未被用来门控 `t`，
故这只是"`t ≥ 0` 由时钟原点保证"，**不是**"由 `tw_start[0]` 检查保证"。

### 2.3 任务 2：G7 温度硬门的逐路径核对

| 路径 | 是否检查 `hard_temperature_bounds_c` | 行号 |
|---|---|---|

| `run_exp_energy_c0.certify_plan` | **否**。纯能源 | `:154-199` |
| `coldchain_state._thermal_violations` | **计算但不拒绝**：返回 `(count, duration)`，调用方只把它写入 metric | `:433-447`、`:309-311` |
| v2 `coldchain_evaluator_a1` | **不计算**温度可行性，**无** `temperature_hard_feasible` 字段 | 全文 |
| v1 `coldchain_evaluator` | **计算**：`temperature_hard_feasible = thermal_count == 0 and thermal_duration <= 1e-9` | `:358` |
| `hard_gate` | **要求且强制**：`coldchain` 列为 required + boolean（`:39-44`），
`hard_pass = all(hard_vector_from_outcome(...).values())`（`:127-129`），
`service_ok(coldchain) = all(hv.values())`（`:146`） | `:39-44, 112-124, 127-129, 146` |

**回答四问**

1. **安装前是否必须满足 `hard_temperature_bounds_c`？**
   **提交前不必须**。`certify_route`/composer/`certify_plan` 三处均**不涉及**温度硬界。
   它只在**终局 outcome 层**（v1 评估器 → `hard_gate`）作为硬门被评估。
2. **温度违规记录是否真正触发拒绝？**
   `_thermal_violations` **本身不拒绝**；但在 **outcome 层**，`temperature_hard_feasible = False`
   会使 `hard_pass`/`service_ok` 为假 ⇒ **终局层会判服务失败**（终局拒绝，非提交前拒绝）。
3. **是否存在"鱼可售通过 + C0 通过 + 温度硬约束违规"的可构造情况？**
   **逻辑上可构造**（三者判据彼此独立，且 v2 品质更新**不含温度**）。
   **在本合同参数下实测不可达**：见下表的数值包络。
4. **补救机制？** 见 §5 的 G7 建议。

**为什么实测不可达（这是本轮最重要的量化发现）**

温度动力学：`_advance_temperatures` 用
`natural = ambient + (T−ambient)·exp(−h·Δt)`，再（制冷开启时）
`updated = max(target, natural − c·Δt)`（`coldchain_state.py:366-382`）。

| 温区 | `ambient` | `target` | `hard_bounds` | `h` | `c` | 平衡点 `ambient − c/h` | 平衡 ≤ target？ |
|---|---|---|---|---|---|---|---|
| 0 番茄 | 25.0 | 18.0 | (0, 30) | 0.20 | 2.0 | **15.000** | 是 |
| 1 冷藏鱼 | 25.0 | 4.0 | (0, 8) | 0.16 | 5.0 | **−6.250** | 是 |
| 2 冷冻鱼 | 25.0 | −18.0 | (−25, −12) | 0.12 | 8.0 | **−41.667** | 是 |

⇒ 制冷**持续压过**热传导（`c ≫ h·headroom`），且 `max(target, ·)` 以 target 为**下限**。
唯一能超过 target 的机制是**开门增温**：`warmed = T + door_heat/thermal_capacity`
（`:413-430`），单次增幅 = 0.0333 / **0.0875** / 0.1200 °C（温区 0/1/2）。
下一个段必定被制冷拉回（降温速率 2.0/5.0/8.0 °C·h⁻¹）。

**实测包络（4 个 cal 实例、7698 段、200 次开门）**：

| 温区 | target | hard_lo | hard_hi | **obs_min** | **obs_max** | 违规 |
|---|---|---|---|---|---|---|
| 0 | 18.000 | 0.000 | 30.000 | 18.000 | 18.033 | **无** |
| 1 | 4.000 | 0.000 | 8.000 | 4.000 | **4.088** | **无** |
| 2 | −18.000 | −25.000 | −12.000 | −18.000 | −17.880 | **无** |

⇒ 观测温度被**钉在 `[target, target + 单次开门增温]`**，距上界余量 **11.97 / 3.91 / 5.88 °C**。
按每次开门 0.0875 °C 估算，温区 1 需**约 46 次连续不降温的开门**才会触界。

**⇒ 同意用户提升 G7 级别，但需精确表述**：
G7 是**结构性缺口**（提交前无温度硬界检查），**在本参数化下不可达**；
**"可构造"指的是逻辑层面，不是本合同的数值层面**。两者**不得混为一谈**——
这与用户对异议一的分类要求是同一条方法论。
