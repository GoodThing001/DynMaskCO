## 2. 适配设计（OR-Tools / PyVRP accept 臂）

- **决策规则**：每次揭示，对每个新订单（按揭示时间序）：
  pool = 已接受未服务 ∪ {o}（committed_next 已在途，排除）→ 求解器求「覆盖全部 pool」的静态
  pickup-to-depot CVRPTW 最小距离计划 → 无完整解/超时/真实 C0 `certify_plan` 能耗 > B → 拒单
  （保旧计划）；否则接受并写回计划。
- **信息边界**：与 SAA 臂同口径——只读已揭示订单 + 车队状态（`_vehicle_serve_state` 锚点语义复用
  `C0ReserveReplanner`），不读未来订单/未揭示字段；场景采样器接口不参与。
- **建模**：镜像 CC_Compare 已冻结适配（OR-Tools-RH-D / PyVRP-RH-D）的整数化与建模语义
  （virtual start 钉时间/载重、eff 容量、dummy 终端、service-first drop penalty、PATH_CHEAPEST_ARC
  + GLS + solution_limit=30、PyVRP required=True + seed=0 + MaxIterations）。
- **口径**：同一 `evaluate_trace_a1` 效用 + 三档 p_c 对同一轨迹独立评价 + 不筛天 + day-clustered
  bootstrap；与步骤 2 gate.json 的 cond_hist/uncond_hist/explicit_feat 逐日行配对。
- **代码**（扩展工作区，不改任何冻结文件）：
  - `scripts/evaluation/solver_accept_replanner.py` — `SolverAcceptReplanner`（双后端）
  - `scripts/evaluation/run_a1_external_accept.py` — 驱动（`--solver ortools|pyvrp`，从步骤 2
    gate.json 读 B/cooling_share，`--final-test` 显式开启才碰测试日）
- **本地烟测（2026-09-26，开发证据）**：两求解器 2 天 × p_c=(5,10,15)：
  hard_feasible=1.0、0 超时、独立重跑逐日逐位一致（确定性 PASS）。
  - ortools_accept 日效用 −488.0 / +425.7（2 天均值 −31.1；拒单主因 = certify_budget 121/200 次决策）
  - pyvrp_accept 日效用 −1123.7 / −274.8（均值 −699.3；certify_budget 147/200）
  - 烟测 2 天方差极大，不构成任何结论；以 40 天正式比较为准。
- **调试中修复的坑（已固化在代码）**：OR-Tools 客户节点 id 与模型节点号方向颠倒
  （`NodeToIndex(真实id)` 越界 → 原生崩溃）；PyVRP `Client.location` 每次访问返回新 wrapper
  （`Model.data()` 按对象 id 对账 → KeyError，须保留 add_location 原 wrapper）；PyVRP 路由里
  depot activity 与首位客户共用 idx=0（须 `is_client()` 门控）。

## 5. 「为什么 CC_Compare 方法很多、适配的却少」+ 2026-09-29 扩充（战役内）

### 5.1 CC_Compare 全量方法 → A-v1 accept 协议的适配性映射

A-v1 对比方法必须能作为「接单决策者」（读 VisibleSnapshot、产出接/拒 + 可认证计划）。
CC_Compare 19 个仓库按适配性分四类：

| 类别 | 仓库 | A-v1 适配性 |
|---|---|---|
| **已适配（A-v1 接单臂，已跑）** | OR-Tools、PyVRP（A-05e 修正后：C1 系统胜 +287.7 / +878.4 主档）；RRNCO（2026-09-29 新增 ordering accept 臂，运行中） | 直接可作「全覆盖可行性接单」决策器 |
| **规则臂（2026-09-29 新增）** | —（无仓库，纯规则）myopic / value-e λ | 合格动态接单规则基线（已跑） |
| **旧协议冻结（另一协议，不参与 A-v1 主表）** | PyVRP-RH-D、OR-Tools-RH-D、RRNCO-Ordering-RH-D（R1 seal）、JF1-H-F | strict-online DCC-VRP 距离协议 |
| **可适配但未做（学习型构造器，需设计「端到端接单」语义）** | AM/POMO（经典构造）、CaDA（约束感知零样本）、RouteFinder（基础模型）、CO-enriched-ML（原生动态 VRPTW 预测+优化） | 需加 reject 动作或「decode→全覆盖 certify 接单」语义；工作量为中 |
| **不适配（判死/无代码）** | PIP-constraint（单车辆 TSPTW，缺容量/多车）；MAPT（无开源，仅论文数据）；GLOP（大规模分区，无决策层）；MVMoE/Omni-VRP/Sym-NCO/SGBS/DeepACO/Learn-Improvement-Heuristics/Learning-to-Delegate（静态构造/改进，硬适配=发明新决策策略，可比性弱） | 详见 `docs/论文参考/对比方法/对比方法总表.md` 与 CC_Compare README 的判死记录 |

**结论**：「仓库多」≠「可比方法多」——多数仓库是静态路由求解器，A-v1 的接单决策层必须由适配层
补上；判死/无代码的另有 3 个。当前已实际跑的外部/规则臂：OR-Tools、PyVRP、RRNCO、myopic、
value/e（+ 内部三臂 SAA）。
