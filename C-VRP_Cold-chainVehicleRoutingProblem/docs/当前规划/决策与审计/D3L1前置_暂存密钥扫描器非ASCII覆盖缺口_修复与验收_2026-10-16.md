## 0. 一句话结论

## 1. 缺口机制（源码行级证据，非推断）

修复前的 `staged_files()`：

```python
out = subprocess.run(['git', 'diff', '--cached', '--name-only', '--diff-filter=ACMR'],
                     cwd=str(repo), capture_output=True, text=True)      # 无 -z
```

`git diff --name-only` 默认 `core.quotepath=true`，**任何非 ASCII 路径都会被 C-引用**。实测（本仓库真实提交
`e8a502e` → `HEAD~1..HEAD`）：

| 环节 | 实测 |
|---|---|
| `git diff --name-only` 输出的“名字” | `"C-VRP_.../docs/\345\275\223\345\211\215\350\247\204\345\210\222/..."`（带引号的转义串，**不是路径**） |
| 把这个串喂回 `git show :<name>` | **returncode = 128**（`staged_content()` 因此返回 `None`） |
| 用真实 UTF-8 路径喂 `git show :<path>` | returncode = 0，14157 字节（blob 本身完全可达） |
| 修复前的分支处理 | `if raw is None: continue` —— **静默跳过，且不进入 `checked` 计数** |

所以丢失的**不是可读性，而是覆盖本身**：`n_staged_scanned` 不包含这些文件，判定仍为 `STAGED_CONTENT_CLEAN`。

**同一根因的第二处证据（非 ASCII 与 `text=True` 相互作用）**：探针在本机以默认 `text=True` 调 git 读取含
非 ASCII 的索引输出时直接抛 `UnicodeDecodeError: 'gbk' codec can't decode byte 0xae`。即该代码路径在 Windows
上不只漏读，还可能**崩溃**；修复后统一改为**字节模式**（`_git_bytes`）读取。

## 4. 修复（最小改动，四条互相独立）

| # | 位置 | 改动 | 作用 |
|---|---|---|---|
| F1 | `staged_files()` | `git diff --cached --name-only **-z** --diff-filter=ACMR`，按 `\0` 切分并以 `utf-8/surrogateescape` 解码 | `-z` 下 git **从不引用**路径 → 非 ASCII 名字变成**可用**的原始名字 |
| F2 | 新增 `_git_bytes()` | 所有 git 调用返回**字节**，不用 `text=True` | 消除 ANSI 代码页解码（gbk）导致的崩溃/乱码 |
| F3 | `scan()` | `raw is None` 时**不再 `continue`**：新增规则 **`R5_staged_blob_unreadable`** 并计入 findings；同时区分 `gitlink`（mode 160000，本身没有 blob，合法跳过） | 把“读不到”从**静默跳过**变成**拒绝**：读不到 = 没扫过 |
| F4 | 计数与判定 | 新增 `n_staged_entries` / `n_unreadable` / `n_gitlink_skipped` / `coverage_complete`；`verdict` 在 `n_findings == 0` **且** `coverage_complete` 时才为 `CLEAN` | 双轴 fail-closed：**覆盖不完整本身即拒绝** |
| F5 | `git_deliver.py` 的**并发写入守卫** | `recent_writers()` 改为**不穿越联结/符号链接**的遍历（`_walk_files_no_links` + `_is_reparse_point`） | 见 §5.6：守卫原先沿 `_bverify_pinned/shadow` 联结把同一份树看了约 3 遍，产生**幽灵并发写入者**并让 `--ignore-recent` 失效 |

- `tools/git_deliver.py` 不再打印无信息量的 `CLEAN (N scanned)`，改为

### 5.6 同族缺陷（本轮交付时被本守卫自己暴露）：并发写入守卫的联结回声

本轮提交**第一次尝试被拒**，理由为“14 个文件在 90 秒内被写入 ⇒ 存在并发写入者”。**逐条核对后判定为假阳性**，
根因与 §1 属同一族（**作用域被静默放大**）：

- `C-VRP.../results/m0_scale/_bverify_pinned/shadow/{data,MASKCO_code,results}` 是指向扩展根目录的
  **NTFS 联结（junction / reparse point）**，而 `shadow` 本身又位于 `results/` 之下 ⇒ 同一份结果树可经
  `.../shadow/results/m0_scale/_bverify_pinned/shadow/results/...` **无限次回声**。
- 实测：对 `acceptance_after_fix.json` 一个文件，`rglob` 命中 **5** 次；`os.path.samefile` 为 **True**，
  即**同一物理文件**，不是副本 ⇒ **没有失控进程、没有磁盘增长**（`_bverify_pinned` 内文件 461 个 / 7.7 MB，
  mtime 停留在 2026-09-24～09-26）。
- 影响量化：扩展目录下 `rglob` 计得文件 **20307**，联结感知遍历计得 **6903** ⇒ **13404 次（约 66%）是回声**。
  守卫因此把同一份树看了约 3 遍，把本轮的 6 个真实文件报成 **14** 条，且 `--ignore-recent` 按路径精确匹配
  无法清除回声路径 ⇒ **守卫在真正需要它的时候不可用**。
- `os.path.islink()` 对 junction 返回 **False**（实测），所以仅仅“跳过 symlink”修不掉它；必须查
  `st_file_attributes & FILE_ATTRIBUTE_REPARSE_POINT`。

**修复 F5 与验收**：改为显式剪枝的遍历后，同一文件命中 **5 → 1**；回声命中 **0**；**真实**近 90 秒写入仍被抓到
（探针文件恰好出现 1 次），`--ignore-recent` 恢复可用。**未**删除、**未**修改任何 `_bverify_pinned` 内容
（它是历史资产，其存在与 mtime 原样保留）。

## 8. 残余与本轮方法论结论

1. **R5 让“覆盖”成了判定的一部分，但仍不是“完整性证明”**：它保证“列出的条目都被读过”，不保证“应该被读的
   条目都列出来了”（例如被 `--diff-filter=ACMR` 有意排除的删除、或 `.gitignore` 之外的特殊索引状态）。
2. **本轮两个缺陷是同一族**：**“静默/隐式地放大或收窄自身作用域的控制”**。
   - 扫描器：作用域被**收窄**（非 ASCII 路径被静默跳过且不计数）→ 已修（F1–F4）。
   - 写入守卫：作用域被**放大**（联结回声把一份树看成三份）→ 已修（F5）。
   - 共同的技术前提是**隐式编码/路径语义**（`core.quotepath`、locale 解码、junction 与 symlink 的区别）。
   建议后续对 `tools/` 内所有 git/路径遍历统一要求：① 面向机器的输出用 `-z` 或显式 `encoding`；
   ② 任何“跳过”必须**计数并可见**，或直接升级为拒绝；③ 遍历必须显式声明**是否穿越链接**。
   本轮**只修了这两个工具与一个验收脚本**，未做全 `tools/` 清扫。
3. **对 Q3 的含义**：这两个缺口都是**工程控制**问题，不是数学规格问题；它们不改变 `G-TMIN`、连续温度证明、
   G5/G6、C2/C3、正式 `B`、L2 七要素、L1 `BLOCKED` 资格裁决这七项 Q3 前置项的任何一条，也不构成它们的替代。
