## 3. 会影响裁决的代码问题（优先交付）

### A-01 / P1：认证异常后未回滚，拒单仍可能留在真实计划

证据：`scenario_saa.py:688–697` 调用 `_try_insert_certified`，捕获 ValueError 后只将 `insert_ok=False`。父类 `run_exp_energy_c0.py:303` 一带先改 `_plan` 再调用 `certify_plan`；认证抛异常时没有执行失败分支的恢复。`plan()` 回放 `_plan`，不按 accepted_set 过滤。

定向注入结果：认证函数写入 `{1:[1]}` 后抛 ValueError，最终 `accepted=[]`、`rejected=[1]`、`plan={1:[1]}`。这可能触发 served_not_accepted，当前 R2 的保守余量不能替代事务回滚。

**交付**：候选计划在局部构造，认证成功后提交；普通不可行、异常、超时三个出口都恢复 saved_plan。补回归：认证中途异常后，计划、accepted/rejected、manifest 均满足一致性，真实执行不服务该拒单。

### A-02 / P1：10 秒计时仍未覆盖提交，外部强对照也缺最终复查

证据：`scenario_saa.py:684–719` 只在每对场景之前查时间，最后一对耗时超过预算后仍直接提交。`on_reveal:729–734` 的快照与编号构造在 t0 前，注释“从快照构造起算”与代码不符。多个同时揭示订单共用一个 t0，而外部驱动逐单重新起计时，批次语义也需统一。

定向结果：限制 0.01 秒，两分支各耗时 0.025 秒，实际 0.051 秒后仍 `accepted=[1]`、`timeouts=0`。`solver_accept_replanner.py:379` 一带求解后 certify 再提交，也没有覆盖整条链的提交前时限判断。

**交付**：从约定的决策入口使用单调时钟 `perf_counter` 与绝对 deadline；采样、状态构造、插入、搜索、认证都读取剩余预算；最后提交前再查一次。明确每单还是每批时限并对所有臂一致。报告真实决策耗时分位数、超时率、fallback 原因；若采用协作式截止，说明单个不可中断调用可能过界。补“最后一个场景才超时”“认证才超时”“多单同时揭示”回归。

### A-03 / P1：异常日留在表内，却被效用统计静默删除

证据：`run_a1_step2_gate.py:71–80` 对异常日写 `utility=None`；其 summarize/paired_all_days 调用的 `run_exp_reserve.py:353` `_stat` 会执行 `x=x[np.isfinite(x)]`。外部 `run_a1_external_accept.py:124–135` 又直接跳过 None 配对。

定向结果：2 天包含 1 个执行异常，`n_days=2`，但 `utility_all_days.n=1`、配对 n=1、CI 只来自成功日。当前 both_ok 硬条件仍会阻止这类批次过门，但“utility_all_days / 不筛天”标签与实际不符。

**交付**：区分完整可评价效用与缺失效用。只要存在执行崩溃/缺失，正式 all-days 效用与配对结论标为“不可裁决”，列出 expected_n/observed_n/finite_n 与缺失 day_id；有限子集可作诊断但不可命名 all-days。继续保留全部违规日；不可事后填 0 或任意罚分以获得显著性。若需有限失败计分，必须在新批次前单独预声明。异常日的能耗/收入未知应记 null，保存异常文本和最后事件信息，而非伪造全 0。

### A-04 / P1：外部比较未校验数据身份，最终测试可能错配开发集

证据：`run_a1_external_accept.py:178–229` 从 baseline 文件按 `(p_c,arm)` 取逐日行，不把 seed 放进 key。启用 final-test 后可将 20260927/28 的 solver 行与 20260926 的 SAA 行按 i 配对；同下标不代表同一天。当前默认也不能对 20260930/20261001 正确选择开发 seed。

### A-05 / P1：OR-Tools / PyVRP 容量适配对小数需求过度保守

证据：`solver_accept_replanner.py:55` `_demand_int` 对非整数需求逐单向上取整；OR-Tools 的 capacity 是 floor(50)、当前载重 ceil，PyVRP 的 pickup 复用相同函数。当前 DGP 需求为 float32 的 U(1,3)，SAA 则按原小数数量检查。

定向结果：20 单各 2.01，真实总量 **40.2≤50**，求解器表示成 **60>50**。这足以把真实可行组合判为不可行，不能用“冻结原适配如此”解释新任务中的不公平。

**交付**：在 A-v1 适配器中对 demand、initial_load、capacity 使用同一足够细的数量单位（例如 1000，具体精度先声明），保持小幅保守舍入与最终真实认证；原仓库冻结文件不动。对两求解器补小数载重、已在途载重、近容量边界的可行性对账。修正前后 OR-Tools 可服务集合需单独报告。R1 本身只修改 SAA，不会自动使全部旧 OR 轨迹失效；这里的新适配缺陷才是必须核对强对照的直接原因。

### A-06 / P1：影子未来插入可以改变 committed leg

证据：`scenario_saa.py:381–405` 把 committed_next 放进普通 route，`_greedy_insert_u:435` 从 pos=0 开始尝试；L1 relocate/swap 也把它当可移动订单。

定向结果：真实 committed_next=1，影子插入未来订单后得到 `[2,1]`。真实车已驶向 1，不能先去 2。影子与 certify 的 T3 同值只证明两函数彼此一致，不等价于与真实事件推进一致；当前用 clock 从 current_node 重演整条在途边，还未利用原 committed_finish。

**交付**：把当前不可撤销段作为固定部分，推进真实剩余在途时间/服务完成后再对 mutable suffix 插入；禁止 relocate/swap 移动固定订单或向 closed/returning 车分配未来订单。用“行驶中、服务中、返仓中”的真实事件快照核对完成时间、载重、能耗、品质和交付集合，不能只让两近似函数互相比对。保留所有旧输入与结果，不把本缺陷直接解释成 cond 无收益的唯一根因。

### A-07 / P1：预训练 encoder 被 AdamW 改动，“冻结”注释不成立

证据：`maskco_scenario.py:133` 把 nnx.Module 放在 `_cvrp` 属性；`train_maskco_scenario.py:81` 对整个 model 构造 AdamW。下划线属性不是 NNX 参数隔离机制，stop_gradient 也不阻止 weight decay。

本地 **Flax 0.10.4** 同结构小型 encoder 探针：`nnx.state(enc, nnx.Param)` 的顶层键含 `_cvrp`；其梯度最大值为 0；一次 AdamW 更新后权重变化最大值约 **1.19×10⁻⁷**。这推翻 09-26 审计响应中“plain 属性不进优化器 + stop_gradient 双重保护”的判断。此探针不是对旧 checkpoint 漂移幅度的实测，旧权重须前后 hash 对账。

**交付**：优化器明确只更新 adapter/生成头参数，冻结分支不参与 weight decay；训练开始/结束保存 encoder 参数 hash、可训练参数路径和数量。预训练收益主消融用同架构、同冻结状态的随机 encoder；若比较可训练随机模型，单列为训练策略比较。不能把冻结/可训练、架构大小与预训练同时变化的差值写成纯预训练贡献。

## 4. 性能优化前需要改正的接口与杠杆

1. **L2b 分析的比较对象仍混合修复。** 初查 `tools/_analyze_l2b.py:14–15` 写死 vote2 和 l2b；核查期间 L2B 已改为 l2b2，但基线仍是 R1 前 vote2，且未验证同 R1/R2 的运行身份；按数组位置相减，没校验 day_id。R1 后 L2b 与 R1 前 V2 的差值包含根因修复，不能归因于“边际定价”。改为显式输入、身份检查和按日配对，统一 bootstrap 随机流。没有修复后 amortized 对照时，先报告同 L2b 内 cond−uncond，L2b−V2 只标混合改动诊断。
2. **步骤 3 会丢失选中的下游配置。** `run_a1_step3_compare.py:68–73` 调 run_arm 时不传 shadow_mode/energy_pricing/future_policy/standby_orders，回落到 amortized/reveal/greedy 默认。应让单一锁定配置贯穿所有 sampler、训练后比较和最终测试，写入 manifest，防止“用 L2c 过信息门、用旧下游测 MaskCO”。
3. **L1 选车优化量写错。** `scenario_saa.py:467` 比较插入后的该车整条 route cost，而非 trial−原 route 的增量。定向例子：已有路线插入只增加 **0.0101**，空车新增 **0.8002**，代码仍选空车。应比较车队总距离增量。T6 仅覆盖一个例子，不能由其 PASS 推出 L1 无回归。先修正并限制候选数/搜索时间，再预声明 L1c2。
4. **L2d 全日预留可能重复计已消耗待命。** 当前 marginal 的 est_used 已含累计能耗，再加 cooling_share×standby_orders 的全日预留。它是启发式，不是剩余资源精确估计，尤其晚时刻可能更保守。先拆已耗、不可撤销剩余制冷、可变尾部、未启动车辆固定成本，预留只作用于未发生部分。若继续 {0,100,200} 网格，保持原尝试记录并写清校准对象。
5. **影子超预算价值属于近似放松。** 保留此前授权的“超预算不置 −1e6”修正；但因此 `_sim_scenario` 不能再描述为“硬预算可部署未来策略的期望收益”。先记录 shadow_energy/B、超额量、接受数、acc−rej 的超额差与真实拒绝原因。下一杠杆可比较“仅移除可撤销未来订单直到预算可行”或预声明连续超额价格，避免重新使用全场景巨额常数抹平信号。固定已接受/committed 订单不可删。
6. **density 使用 REV/e，不包括拒绝损失及增量距离。** 它是离线场景打包启发式，不保证最优。当前 T8 本身给出 reveal=19.43、density=4.20，证明“策略变了”，没有证明“策略改善”。新杠杆可评估 `(REV+p_c−增量燃油)/增量能耗`，但要预声明，不能回改已跑 L2c 的含义。样本场景内可用其完整信息；若使用后见打包，应明确其近似信息放松，不能称为严格在线 rollout。

有限 −1e6 虽消除 −inf，仍会在少数失败场景下主导平均分。因此诊断继续保留 acc/rej 不可行场景数和原因；“非全中惩罚”不足以证明所有 margin 已可靠。

## 5. MaskCO 方法与论文贡献缺口

### 5.1 锁定生成方法仍未实现

当前模型仍是相同 MASK 槽单步独立采样；没有数量头和迭代部分掩码训练/推理。短前缀批样本的 MASK 槽超过 m_max、需求桶未约束连续解码、条件未包含明确的时钟/车队/剩余资源、编码器对照不同架构等 09-26 缺口仍在。修复 multinomial 并不解决这些问题。

MaskGIT 原方法包含随机部分掩码训练与条件于前一轮结果的迭代细化，单步独立采样不能代表该机制。[MaskGIT 原论文](https://arxiv.org/abs/2202.04200)

建议的新实现契约：先采 N，再构造恰好 N 个未来槽；共享集合注意力，随机部分掩码训练和匹配的迭代采样；明确时钟编码、可见与 PAD/MASK 掩码、资源上下文角色；每单联合 token 与桶内解码一致。计数模型主要利用需求信息，车队资源主要用于决策相关表征/场景选择，不能未经论证称车队会改变外生需求分布。初始全部 MASK 的对称槽依靠随机采样逐轮打破对称，必须用联合统计和闭环效用验证，不能只看 CE。

“先采 N”也减少被丢弃的 NULL/过去桶处理与不必要场景成本。若使用旧 200 槽+事后数量校正方案，须报告其分布扭曲；禁止先删除 reveal≤clock 再假称数量头已校准未来数。

### 5.2 品质约束在当前主实验中数学上不绑定

`QualityConfigV2` 初始鱼评分 9、阈值 5，冷藏/冷冻速率 0.01883/0.000278 点每小时。`_advance_manifest_quality_v2` 的速率固定，不读取实际温度。

在合法 22 小时日内，极端上界停留 22 小时后的评分为：冷藏 **8.58574**、冷冻 **8.993884**；降至 5 分分别需 **212.43 小时**和 **14388.49 小时**。所以在当前初始化与返仓期限下，可售硬约束不会改变正常可行接单集合；主效用又不货币化品质。当前不能写“Arrhenius 品质风险驱动决策”或“品质约束带来增益”。

**当前可发表主张的候选方向**：制冷能耗受限、具有多温区差异的动态取货接单；品质作为独立描述性指标。用去能耗预算、去温区能耗差异的预声明消融检查冷链资源是否真正影响策略。若另研究温度驱动品质、不同初始剩余货架期或跨日时域，需真实业务/文献依据与独立协议；不可为了取得正向结果提高主任务衰减率或阈值。

终局评价器与 certify 当前也未形成独立的品质/温控硬认证通道。若今后新任务使这些约束绑定，必须同步认证，不能沿用当前“certify_plan 只查能耗”的接口便声称完整 C0 硬可行。

### 5.3 三层增益须分别成立

| 要支持的结论 | 必须比较 | 当前状态 |
|---|---|---|
| 系统决策优于强方法 | 选定方法 vs 修正适配的 OR-Tools/PyVRP、合格动态接单规则 | 尚无同身份正式结果 |
| 条件需求信息有决策价值 | 相同下游 cond vs uncond | R1 后 2 天与 L2b2 40 天均未过；未证明信息普遍无价值 |
| MaskCO 有独立方法贡献 | 学习生成器 vs 经过开发选择的强条件历史/显式预测器；同架构预训练/随机；单步/迭代 | 锁定生成器尚未落地 |

只靠 uncond SAA 超过 myopic OR-Tools 是系统工程证据，不足以归因 MaskCO。只赢弱 explicit_feat 也不足够：现 sampler 主要按时钟取历史池，不读取当天前缀。应补用 train 历史拟合的条件强预测器（数量/温区/热点联合或简洁潜变量模型），并在同下游校准。真实未来 oracle 与已知 DGP 分布 oracle 只能作为诊断上界，明确区分，不混作可部署方法。

多场景动态路由已有直接先例，贡献应落在资源约束下的条件重构、部署增益与机制证据。[Bent & Van Hentenryck 原论文](https://cs.brown.edu/research/pubs/pdfs/2004/Bent-2004-SBP.pdf)

文献报告的“影子越强→SAA 越好，有理论保底”过度外推。Ulmer 等结果约束的是特定 rollout 与其基策略的改进及顺序一致性条件，并不保证替换更强的近似影子路由器、有限 K、放松预算和超时拒单后的终局表现单调改善。[Ulmer 等原文 §4.3](https://justin-goodson.com/papers/OfflineOnlineStochasticRequests.pdf)
