# 机制实验设计：未来信息 vs 评价时域（②b 三评分对照）

日期：2026-09-22。性质：工作包 ② 的**关键缺失对照**设计。目的：分离 `run_causal_headroom.py` 里 myopic 顺序 oracle（+0.09/+0.11 有害）与 clairvoyant 顺序 oracle（−0.21/−0.27）差距中的两个混杂——**评价时域**与**未来信息使用方式**。

---

## 1. 要回答的问题

因果头腔结果有两个可能的解释：

- **H1（评价时域/代理差）**：myopic 评分 `J_vis`（`evaluate_visible_plan`，假设"无新订单到达 + 贪婪补全已知订单"）是终局价值的坏代理；换成"对已知分布取期望的终局估计"就能恢复收益。
- **H2（未来信息主导）**：即使有终局估计，头腔也依赖**真实未来实现**（哪些具体客户、何时、何地），仅凭其分布无法区分候选动作。

三个评分在同一状态/候选集上的闭环终局成本，直接把 H1/H2 分开：

| 评分 | 评价时域 | 未来信息 | 实现 |
|---|---|---|---|
| ① myopic | 短（已知订单补全） | 无 | `evaluate_visible_plan`（已有） |
| ② 分布期望 | 长（终局 rollout） | **仅已知分布**（重采样未来） | 本设计新增 |
| ③ clairvoyant | 长（终局 rollout） | 真实未来 | `rollout_action`（已有） |

判读：
- ② ≈ ③（都 ~−0.2）→ H1：myopic 代理差，可见状态 + 已知分布**有**可学信号（价值函数方向成立）。
- ② ≈ ①（都 ~+0.09 或 ≈0）→ H2：头腔依赖真实未来实现，支持"未来信息主导"。
- ② 介于两者之间 → 量化"评价时域"与"未来信息"各贡献多少。

---

## 2. 已知分布（从 `generate_coldchain_data.py` 提取，edod=0.5 R1）

50 客户 + depot(0.5,0.5)，`generate_coldchain_instance(50,'R1',50,seed,edod=0.5)`：

| 属性 | 分布 |
|---|---|
| 坐标 | uniform [0.02, 0.98]²（R1 无聚类） |
| 需求量 | 生成器 `rng.integers(1, 11)`，即整数 1–10（capacity//5=10，NumPy 上界不含） |
| 温区 | categorical [0.4 常温, 0.35 冷藏, 0.25 冷冻] |
| 时间窗 | `tw_width=0.2, horizon=24`；`center = dist(i,depot)*10 + U(0,9.6)`；`width = 24*0.2*U(0.5,1.5)`；clip 到 [0,24] |
| 服务时间 | `0.1 + demand*0.05` |
| 动态性 | `n_dynamic = 25`（50×0.5）；动态客户 `reveal_time ~ U(0, max(0, tw_end − dist(i,depot) − service))`；静态客户 reveal_time=0 |

**关键事实**：t>0 时，未揭示客户**全是动态客户**（静态客户 reveal_time=0 已在 t=0 揭示）。故"未来"= 剩余动态客户，其分布完全由生成器确定。

## 3. 注入机制（已确认可行）

`resume_from_snapshot(dataset, snapshot, ...)` 用传入 `dataset` 构造 `StrictOnlineEnv` 并 `validate_snapshot_against_env`：

- 校验 `customer_universe = {i : demands[i] > 0}` 与 `visible_mask = {c : reveal_time[c] <= clock}`。
- **只要保持 50 个客户索引不变、demands 全 > 0、未揭示客户重采样后 reveal_time 仍 > clock**，universe 与 visible_mask 就与 snapshot 一致，校验通过。

因此注入 = 对未揭示客户 `{c : reveal_time[c] > clock 且未 served}` 原地重采样属性（coords/demand/temp/tw/service/reveal_time），重算 `dist_mat`（及 `energy_mat` 等 legacy 字段，若被读取），然后把修改后的 dataset 传给 `resume_from_snapshot` 做终局 rollout。已揭示客户的轨迹/车辆状态由 snapshot 完整恢复，不受重采样影响。

## 4. 重采样算法（② 分布期望评分）

对每个决策点（复用 `run_causal_headroom.py` 的 baseline 轨迹 + snapshot 采集）：

1. 从 snapshot 恢复 incumbent plan `P0` 与 `VisibleState`（复用 `_incumbent_plans_and_vis`）。
2. 枚举候选动作（同 clairvoyant 的 `enumerate_actions_from_plans` + `mutable_ids`）。
3. 对每个候选动作 a：
   - `apply_action(P0, a)` → `_snapshot_with_force` 得到 `snap2`。
   - **采样 N 个未来**：每个未来 = 对未揭示客户 U 重采样属性（见下），得修改后 `dataset^{(n)}`。
   - 对每个 n：`resume_from_snapshot(dataset^{(n)}, snap2, continuation)` → `run_resumed` → `_eval` 终局 `coldchain_cost`。
   - `score(a) = mean_n coldchain_cost^{(n)}`（附 std）。
4. 选 `score` 最小的动作写回（复刻 `sequential_oracle_plan` 的顺序 greedy 结构），推进到下一客户/事件。

**未来重采样（单个客户 c ∈ U）**：按 §2 分布重采样 coords/demand/temp/tw/service；`reveal_time ~ U(clock, max(0, tw_end − dist(c,depot) − service))`（条件于未揭示）。重算该客户涉及的所有 dist_mat 行/列。

## 5. 需拍板的设计决策

**D1（核心）— "已知分布"的确切语义**：② 里重采样"什么"，决定结论的措辞。

- **D1-a（全重采样，推荐默认）**：未揭示客户的**属性 + reveal 时序**全重采样。这是最纯的 `E[J_terminal | s]`，对应价值函数目标。
- **D1-b（仅属性重采样）**：保留真实 reveal 时序，只重采样属性。分离"需要知道未来客户在**何时**到达"与"在**何地/何属性**"。更细，但结论更窄。
- **D1-c（保留未来数量与索引，重采样属性）**：介于两者之间。

建议先做 **D1-a**（一个干净的回答），若结果支持 H1 再补 D1-b 分解。

**D2 — 未来客户数量**：② 是否保留"剩余未揭示客户数"等于真实数量？默认**保留**（= 条件于观测到的已揭示数，未来数量 = 真实剩余数），避免把"数量差异"混进"信息价值"。

**D3 — Monte Carlo 样本数 N**：默认 N=16（终局 rollout 每次 ~0.7s，8 实例 × 2 决策点 × ~17 动作 × 16 ≈ 分钟级，可接受）。报告 mean ± std 与 N 的敏感性。

**D4 — 已揭示客户是否也可重采样**：默认**否**（已揭示是"过去"，必须固定；只有"未来"被重采样）。

## 6. 验收标准

- 在**同一批 CAL 状态/候选集**上产出三个评分的闭环终局成本（① myopic 复用已有；③ clairvoyant 复用已有；② 新增）。
- 报告三者的 per-instance ΔJ 与配对 CI，以及 ② 相对 ①/③ 的位置（回答 H1/H2）。
- 若 ② ≈ ③：把"可部署头腔 ≈ 未来信息"修正为"可部署头腔 ≈ 未来**实现**，但**分布可学**"；若 ② ≈ ①：支持"未来信息主导"，但措辞为"在所测采样预算 N 下"，不写死"信息论无信号"。
