# V2 缺陷复现记录（REPRODUCTION）

> 原始数据：`audit/v1_defect_reproduction.json`（脚本 `scripts/reproduce_v1_defects.py`，
> 只调用 V1 源码、不修改）。实例：X-n101-k25（CVRP）、C101（VRPTW），removed=12 客户。

## D1 客户排序未生效（CVRP 贪心）

- 源码：`standard_pool_search.py` L90 `remaining = list(removed)`；L201-206 计算 `order` 后传入，
  但贪心分支从未消费 `ranking`。
- 复现：同一 removed 集合，`sorted(removed)` 与 `sorted(removed, reverse=True)` 两条相反顺序
  得到**完全相同**的修复路线（`ranking_asc_equals_desc = true`）。
- 影响：三种排序（距离/热图/校准）在贪心算子上无任何行为差别；六配置试选退化。

## D2 VRPTW 忽略算子

- 源码：L112 `for cust in (list(removed)):` —— VRPTW 分支既不使用 ranking，也不区分 operator。
- 复现：greedy 与 regret2 输出完全相同（`greedy_equals_regret2 = true`）。
- 影响：VRPTW 上"两算子×三排序"六配置实际只有一个逻辑；P5-B 中 ORDER_SPLIT 与 MASK/SLOT
  的差异仅来自 split/slot 开关。

## D3 Regret-2 静态（插入后不更新后悔值）

- 源码：L73-87 `remaining = sorted(removed, key=order_key, reverse=True)`，`order_key` 只计算一次；
  随后按该固定顺序逐客户插入。
- 复现（插位增量调用计数）：regret2 = 1627，greedy = 781。k=12、约 65 插位/客户下，
  静态实现量级 ≈ 2·k·65 ≈ 1560；动态实现应为 Σ_{p=1..k} p·65 ≈ 5070。实测为静态量级。
- 影响：后悔值无法反映插入后候选结构变化，Regret-2 退化为"按初始后悔值排序的贪心"。

## D4 距离条件校准缺失

- 源码：L201-206 `use_heat = heat if ranking_name in ("heatmap","calib") else None`
  → 两种排序名共用同一张原始热图，无 `residual_edges` 校准。
- 复现：同一 heat 下两次调用输出完全相同（`same_heat_same_routes = true`）；
  源码中不存在 `residual`、`alpha`、`calibrated.json` 的任何引用。
- 对照锁版：`spatial = -d/scale`、`residual = clip(log(rank_D/rank_H), -3, 3)`、
  `heat = spatial + alpha*residual`（alpha 取自 calibrated.json，锁版冻结值）。

## D5 最短可行插位保护语义错误

- 源码：L58-66 在 `slot=True` 时追加"几何绕行增量最小"的位置，**不检查容量/时窗可行性**。
- 锁版语义（`masked_repair.cpp::choose_slot` regret 分支）：按绕行增量升序扫描全部插位，
  取**第一个可行者**作为保护位；若其不在热图 top-8 中则替换末位候选。
- 影响：当几何最小位置不可行时，保护无效（真正的最短可行位置可能仍被 top-8 排除）；
  SLOT / DIST_SLOT 的"插位保护"语义与论文描述不一致。

## 汇总

P5-V1 中至少 5 项确定性缺陷（D1–D5）+ 6 项机制缺失/简化（冲突池、自适应、bundle 并入掩码、
顺序扰动、SA 工作解、六配置时间片），另有 Python 内核与锁版 C++ 内核的效率差异。
P5-V1 的标准任务结果不能作为冻结网络跨目标迁移能力的证据；P5-V2 将按五版本受控实验分离
（STD_OLD / STD_BUGFIX / STD_FIX / STD_NORM / STD_DIST）。

## D7 共同初解不可行（2026-11-26 开发面板 VRPTW 阶段发现）

**现象**：开发面板进入 VRPTW 部分时，`STD_BUGFIX`/`STD_FIX` 端点被 `check()` 判为
INFEASIBLE，`STD_OLD`（冻结 V1）同样不可行，整批中止。

**定位（V2 侧）**：`nn_witness`（共同初解）在 VRPTW 上只做"最近邻链 + 时窗断链"，
断链后剩余客户若无法插入既有路线就会被**丢弃**（覆盖性缺失）；同时开发实例头部
`NUMBER` 等于构造解车辆数（10–12），使任何构造式初解的 K（11–17）都触发车队超限。
两项叠加导致五版本的共同初解不可行 → 面板失去度量意义（不是算法差异）。

**复现**：12 个开发 VRPTW 实例全部 `ok=False`（修复前 `nn_witness`）。Solomon 上
R101 亦不可行、RC105 在 K=26>25 时不可行。

**修复**：

1. `nn_witness` 重写为确定性构造：VRPTW 按 ready time 升序做"最优可行插位"，
   保证覆盖全部客户；随后 `_shrink_fleet` 把短线客户并入其他路线直到 K ≤ 限额；
2. 开发 VRPTW 实例头部 `NUMBER` 统一对齐为 25（与 Solomon 官方车队上限一致），
   构造解 K 保留在 manifest 的 `k` 字段作为**参考目标**而非硬界
   （`manifests` 记录 `fleet_cap_alignment`，SHA 同步更新）；
3. 复核：Solomon 56/56 初解可行；开发 VRPTW 12/12 初解可行（K=11–17，参考 K=10–12）。

**说明**：这是**协议对齐**而非结果驱动调参——判据是"所有版本的共同初解必须可行"，
与任何版本的最终成绩无关；正式面板使用官方 Solomon 数据（头部 NUMBER=25 本已一致）。

**边界**：`STD_OLD` 仍使用冻结 V1 内部的构造器（不改 V1 源码），其不可行/崩溃如实登记
为 `V1_INFEASIBLE`/`V1_CRASH`，不参与汇总、不被修复、不被掩盖。

## D8 校准热图从未生效（2026-11-26 正式面板启动后发现）

**现象**：开发面板（D6/D7 修复后、本轮之前）240 端点全部通过独立复算，但
`stats.ranking_counts` 恒为 `{0: N, 1: M, 2: 0}` —— 六配置试选的**第三个选项（校准热图）
一次都没被采用**。

**定位**：`core/calibration.py` 把锁版 `calibrated.json` 的路径写成了**本机 Windows
绝对路径**；远端 Linux 上 `locked_alpha()` 抛 `FileNotFoundError`，而池搜索里的
`try: heat_cal = calibrated_heat(...) except Exception: heat_cal = None` 把它**静默吞掉**，
于是 `options` 退化为 `[None, heat]`，校准分支永久不可达。这正是 D4（校准缺失）在一些
环境下的再次发生，且更隐蔽——因为没有任何异常外泄。

**证据**：本次开发面板（`development_results/dev01_pre_D8/`，240 端点）作废保留；
其 `ranking_counts` 第三项恒为 0；远端 `locked_alpha()` 直接复现该异常
（`p5v2_fixed_candidates.py` 未捕获，第一次运行即崩在 `calibrated.json` 路径上）。

**修复**：

1. 锁版 `calibrated.json` 逐字节拷贝进包内 `standard_vrp/core/calibrated.json`，
   解析顺序 = 包内 → 环境变量 `MASKCO_P5V2_CALIBRATED` → 仓库只读路径；
   三者皆缺则**直接报错**（`FileNotFoundError`），不再返回默认值；
2. 池搜索内的校准异常不再静默：写入 `PredictorStats.errors` 并计入 `fallbacks`；
3. 复核：冒烟 `ranking_counts=[2, 0, 1]`（校准选项被采用的直接证据）；
   `locked_alpha() == 0.25`（与锁版一致）。

**影响**：`dev01_pre_D8` 的 240 端点与当时正在运行的正式面板批次全部作废重跑。
该缺陷也解释了"校准热图无效"的表象——它此前根本没有被计算过。
