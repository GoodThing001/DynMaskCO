## 2. 三项交付

### 2.1 交付 A：提交前的 **Ω 成员性资格**

提交门必须**在写入真实状态之前**、对**当前状态版本**验证并记录：

| 检查 | 内容 | 依据 / 现状 |
|---|---|---|
| A-1 热 | 提交后的段前后温度在 `hard_temperature_bounds_c` 内 | 现有实现**只计数**（`_thermal_violations`），**不拒绝**；`_validate_state` **不校验温度** |
| A-2 时间窗 | 每次到达 ≤ `tw_end` | 只在 `certify_route`（计划期）与终端评估器存在；**提交路径无** |
| A-3 容量 | 累计载重 ≤ `shared_vehicle_capacity` | 同上 |
| A-4 返仓 | 返仓到达 ≤ `tw_end[0]` | 同上；**`certify_plan` 根本不引用 `tw_end[0]`** |
| A-5 承诺 | 已承诺 leg 不被撤销、订单恰好取一次 | `_commit` 无校验；靠 replanner 自律 |
| A-6 合法性 | `plan_vehicle_set / revealed_only / no_served_in_plan / no_duplicate_order` | **已在 B3-Q 实现短路顺序**（`d3_composed_certifier`），但**无生产调用方** |
| A-7 身份 | `H(S)/H(C)/H(P)` 三重相等 | 已在 B2 实现，无生产调用方 |
| A-8 时限 | 决策未超时 | 已在 B2 的 `deadline_ok` |
| A-9 能力缺口 | 品质/可售**无保守认证**时**阻断** | 现状 `CAPABILITY_GAP_BLOCKING` ⇒ `installable=False` |

**规格要求**：提交门**必须**把 A-1…A-9 的逐项结果**与状态身份一起**写入回执；任一项失败 ⇒ **不得写入**（fail-closed），且必须记录**是哪一项**。

### 2.2 交付 B：**状态变化后的认证失效**

- **失效触发**：任何使 `(state_hash, contract_hash, effective_contract_hash, profile_hash, plan_digest_anchor_v1)` 之一改变的合法状态变化（reveal 清空可变尾 `strict_online_env.py:528`、clock 推进、服务完成、返仓、重规划改计划）⇒ 已发出的凭据**立即失效**。
- **粒度**：失效是**按 (决策点, 计划)** 的，不是按运行；**不得**把"曾经认证过"当作"现在仍被认证"。
- **检出机制**：安装前**重新计算**三重身份并比对（B2 的 `pre_install_reverify`）；**不得**依赖缓存或时间戳。
- **与 G-C 的关系**：这是 G-C 的必要条件**而非充分条件**——它保证"状态变了就不再放行"，但**不**保证"没有绕过门的写入路径"。

### 2.3 交付 C：**无法认证时的 fail-closed 行为**

**规格：认证不可得 ⇒ 不得提交，且必须进入已定义的安全降级**。可允许的降级按优先级（须由调用方显式声明当前处于哪一种）：

| 降级等级 | 行为 | 说明 |
|---|---|---|
| **D0** | **不提交**，保留当前已提交状态（vehicle 计划不变） | 最严格；对应"WAIT"（`mutable_suffix=[]`），**不产生任何真实状态变更** |
| **D1** | 提交** incumbent（未修改的基线计划）**，其认证状态独立于被拒绝的候选 | 仅在 incumbent **自身**通过 A-1…A-9 时可用；否则退回 D0 |
| **D2** | 提交并**显式标记为"未完整认证"**，且该标记进入回执与后续审计 | **当前不允许**（会解除 D8），仅登记为待裁决设计 |

**硬性要求**：
- fail-closed 不得以**异常逃逸**代替（refuse ≠ crash）；
- **不得**把"认证器缺失"当作默认通过（现状 `run_repair_transaction` 的 `no_certifier` 拒绝是正确范式）；
- **不得**在未认证状态下写入任何真实状态。

## 3. 状态机（可机械检验）

**状态**：`INIT` → `CANDIDATE` → `CERTIFIED` → `STALE` / `REFUSED` / `DEGRADED` → `COMMITTED` → `EXECUTED`

**核心不变式（两条，必须分开检验）**
- **INV-L（局部）**：**不存在**从 `CANDIDATE`/`STALE`/`DEGRADED` 到 `COMMITTED` 的迁移；进入 `COMMITTED` 的**唯一**前置是"在**当前**状态版本上 `CERTIFIED`"。
- **INV-C（持续）**：`COMMITTED` 之后的**任何**状态变化使凭据→`STALE`；且**不存在**绕过门的写入路径（即 `COMMITTED` 的**唯一写入者**是该门）。

**迁移表（守卫 = 进入该迁移必须成立的条件）**

| 迁移 | 守卫 | 失败时 |
|---|---|---|
| `INIT → CANDIDATE` | 候选计划已构造 | — |
| `CANDIDATE → CERTIFIED` | A-1…A-9 全部通过 **且** 能力缺口不存在 | → `REFUSED`（记录具体项） |
| `CANDIDATE → REFUSED` | 任一项失败 / 认证器缺失 / 认证抛异常 | 真实状态**不变** |
| `CERTIFIED → COMMITTED` | **当前**状态版本的三重身份与凭据相等 **且** `deadline_ok` **且** 证书完整 | → `STALE`（需重新认证） |
| `CERTIFIED → STALE` | 任一身份分量变化 | 需重新认证；不可认证 ⇒ `DEGRADED` |
| `STALE → CERTIFIED` | 在**新**状态版本上重新认证 | → `REFUSED`/`DEGRADED` |
| `DEGRADED → COMMITTED` | **禁止**（无此迁移） | — |
| `COMMITTED → EXECUTED` | 由 env 推进（本门不参与） | — |

## 4. 单独登记的**模拟器语义缺陷**（不因计数为零而关闭）

**`_force_return_all` 的卸载记录时刻与冷链物理推进时刻不一致**（独立复核发现，本轮登记为独立项）：

- `strict_online_env.py:658-664`：`_commit(inst, clock, v, traces, 0)` → `:273` 设 `v.return_finish = depart + travel`，而 `:272` 只把冷链推进到 `depart`；随后 `:664` 以 `finish` 调用 `_advance_fleet`，后者以 `depart_time = arrival_time = service_finish = finish` 关闭货物（`coldchain_state.py:391-402`）。
- **后果**：**记录到的**卸载发生在出发时刻，比物理早一个返仓行驶时间 ⇒ 记录的 `delivered_quality` 比物理**更乐观**（对下界是保守的，但会**削弱**任何以交付记录为准的交叉检验，例如 `BND`）。
- **处置（用户裁定）**：
  1. **单独登记**为模拟器语义缺陷，**不合并**进下界讨论；
  2. **不得**因为"当前样本调用计数为 0"就把该风险关闭（本实例 0 次调用、最大返仓到达 15.97 h vs `tw_end[0]=24 h`，但这只是**未触发**，不是**已安全**）；
  3. **不得静默修改历史物理实现**；任何修正须作为新的版本化实现并单独验收。
