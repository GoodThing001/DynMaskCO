V1.20: the execution-entry bypass is closed (12/12 counterexamples)

Independent review found that `main()` accepted `--worker` directly:

    if args.worker:
        return worker(args.out_dir)

That path skipped the human-authorization gate, the one-shot consumption and the supervisor's
deadline containment, yet loaded the F checkpoint and called the scorer -- the entire apparatus
installed for the first blocker could be bypassed with one flag. `--synthetic-command` was a second
opening, because it substitutes the worker process.

Fix: the supervisor is now the ONLY component that can start real F work. After a human-approved
credential has been validated field-by-field against the frozen identity AND consumed one-shot, the
supervisor publishes an EXECUTION CONTEXT (a fresh private 256-bit secret, a one-time nonce, the run
id/dir binding, the consumed credential's digest and receipt path, and an HMAC over that payload).
The real worker's first action -- before importing JAX, before reading the checkpoint, before any
scorer call -- verifies it: file parses, secret present and private, HMAC verifies, run id/dir bound,
the one-shot consumption receipt exists for this run, and the credential still hashes to the digest
that was consumed. A nonce alone proves nothing (anyone can invent one); the consumption receipt is
what cannot be fabricated by the process the gate protects.

Also: an authorization combined with `--synthetic-command` is refused outright, so a one-shot
credential can never be spent on a substituted worker.

One platform limitation is recorded rather than papered over: `os.chmod` cannot express owner-only
on Windows (stat mode is synthesised and reports 0o666 for ordinary files), so the 0600 check is
enforced only on POSIX; on Windows the secret's privacy rests on the run directory's ACL and on the
secret never entering a command line or any record. P1's artifact says so explicitly.
