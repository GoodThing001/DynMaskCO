VERDICT ON THE v2 FISH QUALITY LOWER BOUND: PROVEN for the two fish zones.

Q1 - REAL v2 QUALITY DYNAMICS (facts, with line numbers in the spec)
  First-order tomato: new = q * exp(-rate * duration_h)   (coldchain_state.py:487-488)
  Zero-order fish x2: new = max(0.0, q - rate * duration_h)   (:484-486)
  v2 quality does NOT depend on compartment temperature: _advance_manifest_quality_v2 takes
  (manifest, duration_h, contract) with NO temperature and NO precooled argument, and rates
  purely by q2.rate_per_hour[c] - in contrast with the v1 branch, which takes
  temperature_before/after and runs Arrhenius via quality_rate_per_hour. This is the single
  most important structural fact in this study.
  Time anchor: the v2 branch runs at the START of the segment (:220-222) and the pickup event
  appends the new lot afterwards (:270-278), so a newly picked order accrues no loss on the
  inbound segment and enters at service_finish. Pre-pickup decay therefore does not exist.
  Return settlement: _delivery_record_v2 with end_time = arrival_time on the return segment
  (:286-289, :493-515). active_quality_loss returns 0.0 for v2 (:151-152), so quality is not
  monetised. Threshold: salable = quality_remaining >= threshold[c] - 1e-9 (:501-504).

Q2 - THE BOUND
  Q_LB(c) = max(0, Q_0(c) - k(c) * H_max),  H_max = tw_end[0] * hours_per_time_unit.
  Proof (five steps, each mapped to source): zero-order recursion gives an EXACT loss
  k * sum(dt); the summed dt equals return_arrival minus pickup_finish; that duration is
  bounded by T_end - 0 because pickups occur at t >= 0 and the return is bounded by T_end
  (tw_start[0] = 0, horizon = max(tw_end), _force_return_all at the horizon
  strict_online_env.py:454/506-508/658-664, independently enforced as depot_return_violation
  coldchain_evaluator_a1.py:84); k >= 0 and max(0,.) are monotone.
  T_horizon measured: tw_end[0] = 24.0 and tw_end[0] == max(tw_end) on ALL instances of all
  three m0_scale files.
  Numbers: chilled fish Q_LB = 9.0 - 0.01883*24 = 8.548080 vs threshold 5.0 (margin +3.548);
  frozen fish Q_LB = 9.0 - 0.000278*24 = 8.993328 (margin +3.993).
  APPLICABILITY: zero-order + absolute-threshold fish zones only. NOT the tomato (first-order,
  threshold_type "none"), NOT under a v1 contract, and NOT if T_end > 212.427 h (8.85 days) for
  the chilled zone (the frozen zone only fails at 599.52 days).
  THE PROOF DOES NOT DEPEND ON temperature, Arrhenius, route structure or thermal-violation
  detection, and it uses NO non-public information - so the v1 module's NOT_ESTABLISHED verdict
  neither supports nor undermines it, and the v1 assumptions A2/A3 are simply not needed.
  Empirical: 4 cal instances, 200 delivered records, 0 unsalable, 0 depot_return_violations,
  max return 15.9695, max on-board 14.2224 h, min delivered quality 8.732193 (zone 1) and
  8.996598 (zone 2), both >= Q_LB. No counterexample was found - and, per the repository's own
  standing rule, a bounded search may NEVER be upgraded to PROVEN; the PROVEN verdict rests on
  the analytic proof above, not on this sampling.

TWO OF MY OWN ERRORS, RECORDED IN THE SPEC
  The raw NPZ carries initial_quality = 1.0 for every node (the v1 RATIO convention), so the v2
  absolute path MUST call add_v2_initial_quality, which sets fish zones to 9.0. Two earlier
  probe versions of mine omitted this (one also used the v1 contract) and produced a FALSE
  counterexample ("117 unsalable records, bound violated"). Both were defects in MY probe
  scripts, not in the sources, and are disclosed so the result is not misread.

Q4 - CERTIFICATION INTERFACE GAPS (10 reported; the three blocking ones)
  G1 visible_order_attrs = {} is always empty, so a quality implementation cannot see revealed
     order attributes. The proven bound does not need them, but a general one does.
  G2 the adapter binds contract_version from getattr(contract, "version", None), but NEITHER
     ColdChainContract nor ColdChainContractV2 has a "version" attribute - only schema_version
     ("coldchain-contract-v1" / "coldchain-contract-v2"). So contract_version is always None and
     the strict check at :287-290 can only ever return QUALITY_CONTRACT_VERSION_MISMATCH. It is
     fail-closed, never a false accept, but it BLOCKS every legitimate implementation. The
     repository already has the correct idiom at d3_quality_projection.py:48-55.
  G3 vehicles / served_mask / cargo manifest are stored by reference, not as immutable
     snapshots, and certify_route reads them.
  Also: plan_identity omits anchor_load; the registry is a caller-supplied in-memory dict; all 8
  receipt paths are in-memory only (S-9 asserts a receipt EXISTS, which is not persistence);
  hard_temperature_bounds_c is NOT checked inside certify_route (:179-183 only checks that the
  class is supported) and _thermal_violations only COUNTS (:433-447) - the real verdict lives in
  the v1 evaluator plus hard_gate.py:39-43, outside the pre-submit certification.
  CHECKED AND CLEAN: no v2 tomato miscount. fish_unsalable uses `salable is False`
  (coldchain_evaluator_a1.py:115) and salable_rate excludes salable-is-None from both numerator
  and denominator (:131-134), so salable=None is neither counted as unsalable nor as a rate drag.
