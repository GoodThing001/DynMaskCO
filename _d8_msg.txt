D8: durable install receipt + independent read-back implemented; G0 A-5c closed (7/7)

A-5c was "no durable P_after_install receipt: the ledger receipts are IN-MEMORY only and vanish with
the process". That is now closed, without editing a single byte of the frozen adapter.

Green-phase pattern (same as the G0-Safety batch): d3_geo_adapter.py is a byte-frozen identity whose
exact text is asserted by tests and recorded in freeze trees, and its
checks_this_layer_cannot_perform list legitimately says 'durable receipt (not implemented)' for the
state it was frozen in. So the new capability lives in NEW modules and the frozen module is
untouched:

  scripts/simulation/d3_install_receipt.py   -- write a receipt to a fresh destination name, re-read
                                                it to prove durability, and re-derive the recorded
                                                plan hash from the receipt's own bytes
  scripts/simulation/d3_install_boundary.py  -- RE-EXPORTS the frozen pre_install_reverify /
                                                DECISION_ALLOW / DECISION_REFUSE (verified by object
                                                identity) and attaches the durable boundary to them
  scripts/tests/d3_install_receipt_acceptance.py -- 7 scenarios

Key design points that make the receipt falsifiable rather than decorative:
  * a receipt is written only when the ledger actually installed exactly one plan, and the plan
    handed to the receipt must be the plan the ledger installed;
  * the plan is stored WITH every field plan_hash reads (vehicle id, anchor_node, suffix), so the
    reader can re-derive the hash from the receipt alone instead of trusting its claim;
  * read_receipt always goes back to the bytes on disk, so a reader cannot be satisfied by the
    producer's in-memory dict;
  * R1 re-reads the receipt in a SEPARATE process (`python -c ...`);
  * R2/R3 show that a refused install leaves NO receipt and the reader reports the gap;
  * R4/R5 show tampering with the bytes and mutating the plan value are both detected;
  * R6 shows two installs produce two distinct, non-overwriting receipts;
  * R7 runs the whole boundary and proves (a) the frozen gate is reused by object identity, (b) a
    gate ALLOW with no real install is never reported as an install.

What a receipt still does NOT prove, and is recorded as still open: the environment's own commit
(_plan_and_commit is outside this boundary), state-level rollback, and any quality / C0-energy
property of the installed plan. G0 does not become qualified; D8 stays blocked on its other items.

No live install, no F forward, no comparison, no training. stable_online_gain stays False.
