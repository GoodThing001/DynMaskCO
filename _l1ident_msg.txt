TASK 2 -- PUBLIC-REPO ANTI-RECURRENCE

  No history rewrite and no force push, as instructed.

  CORRECTED ERROR IN THE CLEANUP REPORT (the one you flagged): `git filter-repo
  --replace-text` does LITERAL text matching, so putting a secret's SHA-256 in
  the rules file makes the tool search for a digest that appears in NO committed
  file -- it would report success and change nothing.  That is a SILENT failure,
  worse than an error.  The report now recommends `--path-glob ... --invert-paths`
  (which never touches plaintext), states the content-replacement alternative
  correctly (the rules file must hold the literal secret, live outside the repo
  and be destroyed after use), and adds a per-commit verification loop, because
  an exit code is not evidence.

  DELIVERY-PATH CONTROL: tools/git_deliver.py now calls
  tools/scan_staged_secrets.py after `git add` and before `commit`, and REFUSES
  (exit 4) on a finding.  Rules: R1 secret-file path, R2 bare 64-hex value shape,
  R3 credential assignment including the QUOTED-JSON key shape, R4 PEM header.
  It scans the INDEX (what becomes public), reports PATH + LINE + RULE only and
  NEVER a value, and adds R0: an exempted path whose content is not the redaction
  stub is refused, so an exemption cannot be borrowed.

  ISOLATED SYNTHETIC ACCEPTANCE 10/10 --
  l1_gates/L1_PRECOMMIT_LEAK_PREVENTION_ACCEPTANCE.json -- in throwaway repos,
  with no real secret anywhere.  It proves R1-R4 each refuse, that ordinary
  evidence is accepted, that the stub stays committable, that the scan reads the
  index rather than the worktree, and that no staged literal appears in output.

  THREE SELF-INFLICTED DEFECTS FOUND AND FIXED while building it, recorded here
  rather than hidden:
    * the allow-glob `*/guard/execution_secret_*.txt` was TOO BROAD: it would
      exempt any NEW file of that shape, which is exactly what R1 exists to catch.
      Replaced by exact paths plus a content check.
    * the benign-value regex was UNANCHORED, so `hunter2hunter2` was judged
      harmless and R3 could never fire.
    * a bare `\b` before the key name meant the QUOTED JSON form
      ("pass...": "...") -- the likeliest real-world shape -- was never detected.
    * and the scanner initially REFUSED ITS OWN source and fixtures, because the
      detection literals appear in them; those literals are now split at string
      boundaries.

  REAL INDEX SCAN: 11 staged files, verdict STAGED_CONTENT_CLEAN.

  NOT EXPOSED: .vscode/sftp.json is untracked.  My earlier "tracked: True" was my
  own matching defect and is corrected.

KNOWN LIMITS OF THE CONTROL (stated, not overstated): it is SHAPE-based, not
entropy-based, so a secret embedded in a longer string or base64/split across
lines can evade R1-R4; it only sees the index, so it does nothing about existing
history; and it cannot stop someone bypassing git_deliver.py with a direct
`git commit`.  A real pre-commit hook would be a new engineering task and is NOT
started here.
