## 1. 接线样例：三个阶段必须分开

| 阶段 | 做什么 | 产出 |
|---|---|---|
| `P1_freeze_input_snapshot` | 决策**前**冻结输入身份（**严格 schema**） | `input_snapshot` + `input_decision_id` |
| `P2_call_decide_fn` | 只**调用**，不提交 | `accept`, `diag` |
| `P3_classify` | 候选 / 拟采纳 / 实际提交 + 异常来源 | `plan_variants` / `classify_fallback` / 计数器 |

**同一个快照对象**送给 old / c2 / write_off 三臂 ⇒ 批内逐元素一致；结果类字段
（`action`、`accepted_plan`、`plan_after` 等）**不得**进入该快照，否则
`InputIdentityError`（fail-closed）。此点已由 v2 测试覆盖（含**嵌套**结果键）。

### 1.1 三臂的调用形态

```python
accept, diag = decide_fn(order, ctx)      # old / c2 / write_off 三臂共用同一签名
ea = (diag or {}).get('exception_audit')  # c2 才有；old 恒为 None
```

| 臂 | 起点 | 差异 |
|---|---|---|
| `old` | 冻结旧版**代码身份** | **不得**用新版关掉 C2 冒充旧版 |
| `c2` | C2 版 | `diag` 内含 `exception_audit` |
| `write_off` | C2 版 | 同代码，只**丢弃** sidecar 写入（用于证明写开销不影响决策） |

### 1.2 ⚠️ 只调用 `decide_fn()` 的可声明上限

样例用**桩** `decide_fn` 走完三阶段（零环境依赖，**不产生真实提交**），结果为：

```
commit_status = COMMIT_NOT_OBSERVED
```

即：**只调用 `decide_fn()` 不产生提交回执** ⇒ 至多只能比较 **「拟采纳计划」**
（`diag['plan']`），**不得**标 `COMMIT_OBSERVED`，也不得把"拟采纳"写成"已采纳"。
`plan_variants` 对"声称提交却无权威证据"的情形抛 `CommitEvidenceError`；
被拒绝且已观测到决策结果的情形记 `NO_NEW_PLAN_ADOPTED`（与
`COMMIT_NOT_OBSERVED` 区分）。桩调用落在未观测一侧 ⇒ 正确输出 `COMMIT_NOT_OBSERVED`。

## 2. hi/lo 可观测性证明（能力边界）

用**真实** `role_c_opportunity_cost.shadow_price_budget` + **合约定注入器**
（`calls` **只在成功返回后**追加），逐场景记录 wrapper 能**直接**看到什么。
**未触碰** `role_c_forward.py`。

| 场景 | 成功返回次数 | 异常预算点 | 异常类型 | `λ_B is None` | `undefined` |
|---|---|---|---|---|---|
| `normal_two_budget_points` | 2 | — | — | False | False |
| `hi_timeout` | 0 | `hi` | `DecisionTimeout` | True | True |
| `lo_timeout` | 1 | `lo` | `DecisionTimeout` | True | True |
| **`hi_nan_forward_invalid`** | **2** | **—** | **—** | **True** | **True** |
| `lo_unfinished_then_deadline` | 1 | `lo` | `DecisionTimeout` | True | True |

### 2.1 分层结论

| 观测对象 | 层级 | 依据 |
|---|---|---|
| 预算点**成功返回** | **DIRECT** | `calls` 长度在成功返回后增加 |
| 预算点**异常退出** | **DIRECT** | 异常被捕获后写入 `exception_audit`（类型 + 预算点） |
| 预算点**评估进入** | **INFERRED** | wrapper 只看得到"被调用过几次"，看不到"进入评估"事件本身 |
| 逐**场景开始** | **NOT_VERIFIABLE** | 预算点内部不暴露给 wrapper |
| 逐**场景完成** | **NOT_VERIFIABLE** | `last_diag` 只在 `forward_value` 正常返回后更新 |
| 返回时是否完成**全部场景** | **NOT_VERIFIABLE** | 同上 |

### 2.2 关键反例（本轮新增）

`hi_nan_forward_invalid`：注入器**两次**预算点调用都**成功返回**，但 `λ_B` 为
**NaN** ⇒ `shadow_price_budget` 返回 `None` 且 `undefined=True`，且
**没有** `exception_audit`。

⇒ **`calls` 长度 = 2 与"预算评估有效完成"之间没有蕴含关系**。
因此：

1. `n_successful_budget_returns == 2` **不得**被解释为"预算点评估正常完成"；
2. 预算点评估的有效性只能由 `λ_B is not None` / `undefined` 判定，
   而这属于**结果有效性**、不属于**完成度**；
3. hi/lo 的逐场景 `n_scenarios_entered` / `n_scenarios_completed`
   **必须**写 `NOT_VERIFIABLE`，**不得**用推断值冒充事实，
   **不得**为补齐 schema 而改 `role_c_forward.py`。
