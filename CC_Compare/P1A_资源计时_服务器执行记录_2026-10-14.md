## 2. 计时**前**的核集占用检查（用户明确要求）

`role_c_timing.affinity_contention([0..7], sample_s=2.0)`（读 `/proc/stat` **每核** jiffies 差，
只统计 affinity 集合 —— `loadavg` **不能**证明钉住的核上没别的任务）：

```
external_busy_ratio = 0.2803   (n_cpus_sampled = 8)
per_cpu = {0: 0.4324, 1: 0.0107, 2: 0.4615, 3: 0.2746,
           4: 0.0155, 5: 0.6294, 6: 0.0052, 7: 0.4010}
loadavg = (37.56, 34.91, 33.13)
```

**按事前写死的判据**（`CONTENTION_RULE`：`external_busy_ratio > MAX_EXTERNAL_BUSY_RATIO(0.5)`
⇒ `qualified=False`），**0.2803 ≤ 0.5 ⇒ 不算"明显竞争"**，故继续。
⚠️ 但**逐核**显示核 0/2/5/7 有明显外部负载（0.43/0.46/0.63/0.40），核 1/4/6 近空载 ——
该细节一并留痕，供复核；**判据不因看到逐核细节而事后调整**，
也**不**临场换核集或增加 workers（用户明确禁止）。

## 3. 冻结管线对齐：**锚点在服务器上逐位相同**

`--dry-run`（只搭单元 + 捕获决策点，**不产生耗时结论**）在服务器以
`OMP/MKL/OPENBLAS/NUMEXPR=1` + `taskset -c 0-7` 运行，输出：

```
budget         = 710.6548152249378   （冻结锚点 710.6548152249378，rel_gap = 0.0）
cooling_share  = 3.7208946347769882   （冻结锚点 3.7208946347769882，abs_gap = 0.0）
n_contexts     = 8   （真实决策点）
decision_points_digest = 5b432f2826ea66622173ecc514378bae8d11013374d4e93ad7940a392b2de3dc
```

**这解决了一个此前的悬案**：本机（Windows）同一命令的 `B` 有 `1.76e-5` 的微差
（相对 2.5e-8）；在**服务器**上差值为 **0.0** ⇒ 该微差是**本地平台/版本层面**造成的，
服务器管线与冻结锚点**完全一致**。（差值当时即如实写在 `anchor_check` 里，未藏进容差。）

另：进程实测 `Threads: 1`、`affinity: [0..7]` ⇒ 线程上限与核集都**真的生效**了。

## 4. 启动参数（正式计时）

* 内层：`taskset -c 0-7 <cc_compare python> -u role_c_timing.py --out /tmp/rolec_timing_report.json
  --n-decisions 200 --capture-n 8 --warmup 2`；
* **外层监督器**：`role_c_timing.run_supervised(argv, total_wall_s=46800)` ——
  46800 = 登记的 **43200**（**测量区**上限）+ **3600**（搭单元/捕获的额外预算）。
  这样"已登记上限"同时是"已执行硬上限"（超时即**硬杀并回收**子进程）。
* 决策点集合在计时前**已固定**（上面的 digest），**不得**在看到某些状态耗时高后剔除；
  `records` 保留**完整单次耗时**（含超时/失败）。
