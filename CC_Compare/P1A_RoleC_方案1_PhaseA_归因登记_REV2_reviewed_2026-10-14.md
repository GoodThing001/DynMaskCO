## 3. 计量分母 `T_decision`（**精确定义**）

```
T_decision(d) := perf_counter() 环绕「对决策点 d 的**一次** decide_fn(order, ctx) 调用」
              （进入前取 t0、返回后取 t1；t1 − t0）
```

* **单位**：秒。**不含**预热（`warmup` 调用不计入；且预热次数事前写死）。
* **分母唯一**：所有分区份额的分母**都是** `T_decision(d)`（逐决策点各自的分母，
  不是"所有决策点总和"）。
* **上游不计入**：捕获决策点那一趟（搭单元 / 跑一天 / 场景抽样之外的 env 推进）
  **不进入** `T_decision`；只在报告中单独列出其墙钟，供解释用。
* **仪器自开销**：必须先把"空仪器"（不挂任何分区、仅挂总计时）跑一遍，测出
  **仪器自开销**并在报告中列出；若对账不通过（§4.3）则判 `inconclusive_accounting_error`。

## 4. 互斥时间分区（**正式 50% 判据唯一允许使用的口径**）

### 4.1 inclusive vs exclusive（两套都记，用途不同）

* **inclusive time**（含子调用）：`T_i^incl` = 函数 `i` 及其**全部后代**在本次决策内的
  墙钟累计。**用途：定位热点**。⚠️ 同级 inclusive 之间**可以重叠**，**不得**用于份额分解。
* **exclusive time**（净自身）：`T_i^excl` = `T_i^incl` 减去**所有被统计后代**的
  inclusive 时间 ⇒ 即"只属于 `i` 自身"的时间。**用途：互斥分解与 50% 判据**。
* **采集机制**：在**独立分析脚本**里用包装器实现（**不改生产代码**）；
  维护一个"当前活动叶子栈"，每个包装器把自己的 inclusive 时间累加到自身，
  并把**正在活动的最近后代**的 inclusive 时间从其 exclusive 中扣除
  （标准 self-time 归属）。

### 4.3 独立计量与对账（**REV2 重写；消除恒真式**）

用户复核指出：REV1 的 `P9 = T_decision − Σ T_i` 再用 `|Σ T_i + P9 − T_decision| ≤ tol` 验收，
**数学上恒为零** ⇒ 既查不出**重复计量**，也查不出**漏测**（所有叶子漏测时 P9 会吞掉全部耗时）。
REV2 改为**三通道互不派生的计量 + 离线独立重算**：

**（i）通道 A：每叶 exclusive 累加器（exit 侧）**
每个包装器维护 `child_time`；退出时 `A_i += (t_exit − t_enter) − child_time`，
并把 `(t_exit − t_enter)` 累加进**父**的 `child_time`。⇒ 只统计"自己是**最内层活动**"的时间。

**（ii）通道 B：栈管理器的空档累加器 `G`（enter 侧，独立代码）**
栈管理器在**进入**新叶子时执行 `G += t_enter_new − t_last_exit`（若 `t_enter_new < t_last_exit`
则说明**事件序错乱** ⇒ 直接 `inconclusive_accounting_error`），并在**决策帧退出**时累加尾部余量。
`G` 由**栈管理器**维护、**不由 `T_decision` 派生**、也**不由 `A_i` 派生**。

**（iii）通道 C：离线区间扫描（原始事件表）**
完整事件表 `(label, enter_ts, exit_ts)` 落盘；**跑完后离线**用一个**独立算法**重算：
* 栈纪律：每个 exit 必须匹配**最内层** enter（LIFO）；enter/exit 一一配对，无未匹配事件；
  时间戳单调不降；同一叶子**不得在栈上同时出现两次**（重入即视为**重复插桩**）；
* 父子包含：每个叶子区间必须落在其**声明父**的区间内；
* **最内层活动区间两两不相交**（用区间扫描**验证**，不得假定）；
* 由原始区间独立求和得到 `Σ A_i^offline` 与 `G^offline`。

**验收（非恒真）**：
```
① |Σ A_i − Σ A_i^offline| ≤ max(5 ms, 1% · T_decision)     # 通道 A vs 通道 C（不同算法）
② |G − G^offline|          ≤ max(5 ms, 1% · T_decision)     # 通道 B vs 通道 C
③ |Σ A_i + G − T_decision| ≤ max(5 ms, 1% · T_decision)     # 三通道闭合（可失败：见下）
④ 结构不变量全部通过（LIFO / 配对 / 单调 / 包含 / 不相交）
```
⚠️ **③ 为什么不是恒真式**：`Σ A_i` 与 `G` 由**两段不同的代码**在**不同的时刻**更新
（一个在 exit、一个在 enter），且 `T_decision` 由**第三个**计时器（帧）给出。
**异常路径**（叶子内抛错但未走到累加）、**重复插桩**（同一包装器装两次）、
**事件序错乱**都会让 ③ 失败 —— 这正是它要抓的东西。
④ 的两两不相交由**离线扫描**给出，与在线累加器**互不派生**。

**辅助诊断（不构成验收证据）**：
`P9_residual := T_decision − Σ A_i − G`，**仅作诊断上报**；`P9_residual ≈ 0` **不能**充当
分区正确的证据（用户明确要求）。真正用于裁决的是 `P9_measured := G`。

**fail-closed**：①②③④ 任一不通过 ⇒ 本次决策判 `inconclusive_accounting_error`，
**不得**计入份额统计；若失败率 > 0 ⇒ 整体结论为 `inconclusive_accounting_error`
（**不得**降级成"无瓶颈"）。

**`P9_measured` 占比重时**：若 `G` 本身是最大项且中位数份额 ≥ 0.5 ⇒ 判
**`inconclusive_attribution_incomplete`（归因不完整）**，**不得**报"无主导瓶颈"
（用户明确要求：P9 吞掉大头说明漏测，而不是"没有瓶颈"）。

  （在线 10 s 下可能被截断，而 A 类跑完了完整路径）。
  A 类**只用于成本归因**，**不得**当作在线行为证据；A 类与 B 类的耗时
  **绝不合并**成一个时间占比（见 §5.2 末）。

#### 5.1.2 截断处置（**REV2 明确"保留截断位置"**）

* 若任一决策点在**其 600 s 上限内仍未完成** ⇒ 该次判 **`inconclusive_censored`**。
* **不得**把未完成的函数当作**零成本**；**不得**把该情形判成**"无单一主导瓶颈"**。
* **必须保留的信息**（用户强要求）：截断**发生在哪个叶子/哪个场景上**
  —— 记 `leaf_at_truncation`（§4.2 叶子标签）、`scenario_index_at_truncation`、
  `n_scenarios_completed_at_truncation`、`elapsed_s_at_truncation`。
  **不得**只写"超时"两个字。
* 份额统计**只在完成的决策点**上算，并**一并列出**被截断的**条数**与**叶子**。
* **收束规则（REV2 明确）**：**只要存在任一 `inconclusive_censored`，
  就不得进入 §6 的瓶颈判定** —— 直接按 `inconclusive_censored` 上报并停止。
  （A 类完成的决策点可作**诊断信息**列出，但**不**产出主导叶子结论。）

### 5.2 B 类：在线截止诊断（**保留原 10 s 截止**）

目的：回答"**10 秒截止到来时算法执行到了哪一步**"（这正是用户指出的关键问题）。

逐决策点必须记录：

| 字段 | 说明 |
|---|---|
| `forward_entered` | 前瞻是否**实际进入**过 |
| `evaluation_status` | **三态互斥**：`not_entered` / `completed` / `timed_out`（另有 `error`） |
| `n_scenarios_entered` / `n_scenarios_completed` | 进入/完成了几 个场景（`K=10`） |
| `stages_entered` | 本次进入过哪些阶段（对 §4.2 叶子的布尔掩码） |
| `deadline_hit` | 是否触发内部截止 |
| `timeout_reason` | 触发时的原因串（如 B3 路径） |
| `boundary` | 事前边界规则命中（尤其 `B3_lambda_undefined`） |
| `action` | accept / reject |
| `lambda_B` / `e_o` | 判决所用数值 |

⚠️ **三态语义（用户强要求）**：`not_entered`、`completed`、`timed_out`
**必须是可区分的三种状态**；**不得**一律填 `deadline_hit=false` ——
否则会把**未观察到的信息**写成**否定证据**。
字段缺失时：要么**明确标记不适用并给出结构性理由**，要么判**记录不完整**；
**不得**凭汇总结果反推具体动作。

**报告分离要求**：A 类给出分区份额；B 类给出阶段进入率、场景完成数分布、
B3 触发次数与动作分布。**两者不得合成一个"耗时占比"。**

### 5.3 L1 / L2 / L3 的次序与边界（用户同意）

* **L1（确定性计数）**：不改生产代码的计数包装，输出各调用点的**调用次数/候选数**。
  **只作解释证据**（用于解释 L2 的份额），**不参与**主导判定。
* **L2（分段计时）**：按 §4 的互斥分区测量，**主导判定由 L2 承担**。
* **L3（采样 profiler）**：**仅在 L1 与 L2 互相矛盾时另行申请**；
  **不得自动触发**，且**不得**用来**事后推翻**已经锁定的 50% 门槛。

## 6. 50% 判据（**只用互斥 exclusive 分区**）

### 6.1 逐决策点份额

```
share_i(d) = T_i^excl(d) / T_decision(d)          # i ∈ 叶子集合（P1..P8）
```

### 6.2 预声明的汇总规则（**REV2 重写：两个条件必须指向同一叶子**）

```
i* := argmax_i median_d share_i(d)                     # 唯一候选主导叶子
主判据：median_d share_{i*}(d) ≥ 0.5
稳定性：Σ_{d=1..8} 1[ i* = argmax_i share_i(d) ] ≥ 6     # ★ 同一 i*，不是"各自 argmax 之间一致"
```

⚠️ **REV1 的缺陷（用户指出）**：只要求"逐决策点 argmax 一致 ≥6/8"，
会出现"中位数最大的是 `P7a`，但多数点排名第一的是 `P7b`"却被拼在一起称通过。
REV2 把稳定性判据**显式绑定到 `i*` 这一个叶子**。

**并列最大值的判定规则（事前写死）**：
* 逐决策点的 `argmax_i share_i(d)` 并列时：取**叶子编号最小**者
  （按 §4.2 的固定顺序 `P1<P2<P3<P4<P5<P6<P7a<P7b<P7c<P7d<P8`）；
* `i*` 的中位数并列时：同样取**编号最小**者；
* 报告**必须列出所有并列组**（哪些叶子并列、并列在哪些决策点上）。

**必须上报**：**全部** 8 个决策点的**完整份额分布**（不只报中位数与最大值），
以及每点的 `T_decision`、`Σ A_i`、`G`、`P9_residual` 与 ①②③④ 四项验收结果。

⚠️ **禁止**事后挑一个"恰好超过 50%"的决策点作为整体主导证据。

### 6.3 四档结论（**REV2：新增"归因不完整"档**）

| 结论 | 条件 | 处置 |
|---|---|---|
| **达到门槛** | `median_d share_{i*} ≥ 0.5` ∧ 稳定性（同一 `i*` ≥6/8）∧ 该叶子**不属结构性乘数组**（§6.5） | 允许进入 Phase B 登记（仍需用户裁定） |
| **未达门槛** | `max_i median_d share_i < 0.5` ∧ 稳定性满足 ∧ 无截断 ∧ 对账通过 | 触发 §9 分叉①（**按 §9 措辞**收束） |
| **★ 归因不完整** | **`P9_measured`（=`G`）为最大项且中位数份额 ≥ 0.5** | 判 **`inconclusive_attribution_incomplete`**；**不得**报"无主导瓶颈"（漏测吞掉大头 ≠ 没有瓶颈） |
| **不确定** | 有截断（`inconclusive_censored`）／对账失败（`inconclusive_accounting_error`）／数值不确定（`inconclusive_numeric`）／**字段缺失（`inconclusive_record_gap`）**／稳定性不满足（`inconclusive_unstable_hotspot`） | 记对应 `inconclusive_*`；**不得**写成"无单一主导瓶颈"，**不得**据此进 Phase B |

### 6.4 已删除的替代判据

草案"L1 候选数占比 ≥50% 且 L2 耗时与其一致"**已删除**：调用次数多 ≠ 耗时占比高；
L1 仅解释、L2 定夺。

### 6.5 结构性乘数组（**REV2：废除"乘数 ⇒ 不可优化"的过强推断**）

**结构性乘数组** = 其**调用次数**由协议固定的叶子：`P7a`、`P7b`、`P7d`
（每决策 `K` 场景 × 预算两点 × 场景内未来订单数这一层的展开）。

⚠️ **REV1 的错误（用户指出）**：把该乘数**直接**当作"必要工作量 ⇒ 不可优化"。
**调用次数固定 ≠ 单次内部计算不可优化** —— 每次调用内部仍可能有语义等价的实现级改进
（共享计算、避免重复整算、增量更新…）。本版**废除该自动推断**。

⇒ 若 `i*` 落在结构性乘数组内：

* Phase A **只测"成本在哪里"，不测"有多少实现级余量"** ⇒ **Phase A 单独无法裁决**该叶是否可优化；
* 结论记为 **`dominant_in_structural_group_slack_undetermined`**，
  **按 §9 分叉① 的措辞收束本轮单杠杆路线**，但**必须同时写明**：
  **这不构成"该计算无法优化"的结论**；
* **"必要工作量 / 不可优化"标签在本轮禁止贴**：只有在**事前定义的证据**支持
  "该成本确实无法通过本轮单一杠杆优化"时才允许 —— 本轮**没有**这样的预声明证据，
  故该标签本轮**不可用**；
* 若将来要判定这一点，须**新的预注册**，且其 Phase A 必须**显式包含"实现级余量"判据**
  （例如可复算的重复工作量指标），不得沿用本件。

## 7. 语义等价检查（Mode C；Phase B 之后才用）——**含零/缺失/非有限规则**

在**旧版 vs 新版**、`time_limit=∞`、同一固定决策点集合下逐条比对。

### 7.1 逐条比对项

1. `action`（accept/reject）序列**逐位相同**；
2. `boundary` 与 `reject_reason`（若拒）**相同**；
3. 数值项 `λ_B`、`e_o`、`myopic_net`、`net_after_opportunity_cost`：按 §7.2 规则判等；
4. 被采纳计划 `plan_of` **逐位相同**（同车同序）。

### 7.2 **数值比较规则（写死；REV2 分离"字段缺失"与"显式 `None`"）**

⚠️ **REV1 缺陷**：原表把"两侧均缺失（`None`）⇒ 等"写成一条，**混淆了
"字段根本不存在（`key not in record`）"与"字段存在且为显式 `None`（结构性未定义）"**。
后果：**新旧两版同时漏记 `λ_B` 也会被判成语义等价** —— 那是记录缺口，
不是等价证据。REV2 把两者分离：

| 情形 | 判定 |
|---|---|
| 两侧均为**有限** | `\|a−b\| ≤ max(1e-12, 1e-12 · max(\|a\|,\|b\|))` ⇒ 等；否则**不等** |
| 两侧均为 **0**（含 `+0.0`/`−0.0`） | **等** |
| 两侧字段**都存在且均为 `None`**，且各自带**一致的原因码**（该字段在本决策点**结构性不适用**，例如 `e_o = 0` 时 `λ_B` 按 B1 恒为 `0` 而**不是**未定义） | **等**（报告中标注"两侧都显式未定义，原因一致"） |
| 两侧字段**都存在且均为 `None`**，但**原因码缺失或不一致** | **`inconclusive_numeric`**（不做等值断言） |
| **任一侧字段不存在**（`key not in record`） | **`inconclusive_record_gap`** —— **记录缺口**，**绝不判等**；"两边都没记"**不是**等价证据。结构性不适用**必须显式写出该字段并标不适用**，不允许省略字段 |
| **一侧 `None`、另一侧有值** | **不等**（FAIL） |
| 任一侧为 **NaN / ±Inf** | **`inconclusive_numeric`** —— **不得**当作"等"；NaN 表示"未定义"（例如截止被触发），把它算作匹配等于把不确定性当证据 |
| 两侧为**同号** Inf | 仍判 `inconclusive_numeric`（不做等值断言） |

**前置字段存在性检查**：逐值比较**之前**，必须先断言两侧记录的字段集合完全一致
（`REQUIRED_FIELDS` ∪ 条件必填字段；条件必填的触发条件两侧同样要一致）。
集合不一致 ⇒ **`inconclusive_record_gap`**（fail-closed），**不进入**逐值比较。

⚠️ 相对误差 `≤1e-12` **对零值不完整**（这正是用户指出的问题）⇒ 上表把零、**显式 `None`**、
**字段缺失**、非有限**分别**写死。**任何 `inconclusive_numeric` / `inconclusive_record_gap`
⇒ 本次一致性检查不给通过。**

### 7.3 报告要求

必须给出**全部**决策点的逐条比对记录与"不一致条数"，
**不得**只给汇总结论；耗时不参与等价判定（耗时差异与语义等价是两件事）。

## 11. 结论词典（`inconclusive_*` 的精确定义）

| 状态 | 含义 | 禁止的读法 |
|---|---|---|
| `inconclusive_censored` | A 类在**外层上限（`600 s`/决策点，`12 000 s`/Phase A）内**未完成（有截断） | ❌"未完成的函数成本为 0"；❌"无单一主导瓶颈"；❌ 只写"超时"而不给截断位置 |
| `inconclusive_accounting_error` | §4.3 对账不通过 | ❌ 计入份额；❌ 降级为"无瓶颈" |
| `inconclusive_numeric` | §7.2 出现 NaN/Inf，或**两侧均为显式 `None` 但原因码缺失/不一致** | ❌ 当作"等"；❌ 通过一致性检查 |
| `inconclusive_record_gap` | **字段缺失**：任一侧记录**不含**被比对字段（`key not in record`），或两侧字段集合不一致 | ❌ 当作"两边都没记 ⇒ 等价"；❌ 通过一致性检查；❌ 用"结构性不适用"为由**省略**字段（必须显式写出并标注） |
| `inconclusive_attribution_incomplete` | §6.3：`P9_measured`（`G`）为最大项且中位数份额 ≥ 0.5（**漏测吞掉大头**） | ❌ 写成"无单一主导瓶颈"；❌ 把 `P9_residual` 当独立证据去凑分区；❌ 进 Phase B |
| `inconclusive_unstable_hotspot` | §6.2 稳定性不满足（同一 `i*` 出现 `<6/8` 次） | ❌ 写成"无单一主导瓶颈"；❌ 进 Phase B |

### 13.3 登记件之外的**新发现缺陷**（只报告，**未修**）

**发现**：`CC_Compare/P1A_资源门登记.json` 在封存裁定里登记了 raw SHA-256
（`6d0e57c6d46bf46a61005b8f4d27edd99d8641dd47675e508c39c155f1a635bf`），
但它在 `CC_Compare/.gitattributes` 里**没有任何条目**（`.gitattributes` 只列了
`/P1A_资源门登记_模板.json`，即模板，不是这份实际登记）。

**实测后果**（用 `tools/_check_phasea_registration_doc.py` 可复现，只读）：

```
P1A_资源计时_报告_2026-10-14.json    worktree == blob == df914198…   ✅
P1A_资源计时_监督器_2026-10-14.json  worktree == blob == bc29105b…   ✅
P1A_资源计时_进度原件_….jsonl        worktree == blob == 6f2ba2a2…   ✅
P1A_资源门登记.json                  worktree = 6d0e57c6…（CRLF，= 登记值）
                                     blob     = 020fc0e7…（LF）        ❌ 不等
```

⇒ **该登记哈希只能在"行尾为 CRLF 的 checkout"上复现**，
在 LF-normalizing 的 checkout（如服务器）取出的字节**对不上封存登记值**。
其余三份登记容器都满足 `.gitattributes` 头声明的 `blob == worktree bytes` 纪律，**只有这一份破例**。

**为什么我没有直接修**：补 `/P1A_资源门登记.json text eol=lf` 并 `--renormalize`
会把该文件的 raw SHA 从 `6d0e57c6…` 变成 `020fc0e7…`，
而 `6d0e57c6…` 已写进**已封存**的 `P1A_RoleC_收束裁定_2026-10-14.md` §2。
改哈希 = 动封存证据，**超出本轮授权**。

**请你裁定**（三选一）：
* (a) 补 `.gitattributes` 条目 + renormalize，并在裁定件里**追加一行**"资源门登记行尾归一后 SHA 变更"的更正记录（**旧值保留、不擦除**）；
* (b) 保持现状，把"该哈希仅在 CRLF checkout 可复现"作为**已知限制**登记，不改文件；
* (c) 改为把 raw SHA 一律定义为"LF 归一后的字节"（需同时重算其余容器，代价最大）。
