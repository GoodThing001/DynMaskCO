## 1. 为什么必须有这一层（不是形式主义）

资格矩阵里 **6 个"受 CPU 争用"臂**的根因就是 **worker 数 × 每 worker 线程数**把机器
过度订阅——`lih_51015` 曾达 **54.225 次超时/天、单决策 50.79 s**，而当时代码身份与 v1
**完全相同**，**从记录里看不出**配置差异。⇒ 若不显式登记并记录线程/亲和性配置，
"某臂很慢"既不能归因、也不能复现。

## 3. 候选上限（**请用户逐项裁定或改写**）

| 项 | 建议值 | 理据 | 代价 / 风险 |
|---|---|---|---|
| `OMP_NUM_THREADS` | **1** | 规格 §6 明确要求 | 单进程数值例程变慢；但消掉过度订阅 |
| `MKL_NUM_THREADS` / `OPENBLAS_NUM_THREADS` / `NUMEXPR_NUM_THREADS` | **各 1** | 规格只点名 OMP；**只设 OMP 不足以**消掉 BLAS 线程（numpy 走 MKL/OpenBLAS）——这正是"6 个臂"那类事故的完整修法 | 同上；三者与 OMP 一起设才自洽 |
| `workers` | **8** | 96 核机器上只占 **8 核**（≈8.3%），与共享用户不冲突；`workers` **只影响墙钟、不影响轨迹**（冻结配置 `frozen_config_note.workers` 已写明），故可自由登记 | 40 天 × 200 单的墙钟变长；若太慢可**重新登记**更大值（属资源门变更，不是效果门） |
| CPU 亲和性 | **`taskset -c 0-7`**（与 workers=8 对齐） | 固定核集 ⇒ 计时可复现、且不与他人争同一核 | 若他人恰好也用 0–7 则仍有争用 ⇒ 计时须记录 loadavg |
| 单决策上限 | **10 s**（= 冻结 `time_limit`） | 冻结配置；**不得**据计时结果放宽 | 超时即降级为拒单（既有语义）；须报告超时次数 |
| 总墙钟上限 | **待定**（先用 2 天工程烟测测单日墙钟再反推？——**但烟测被禁止**） | ⇒ 建议改为：先只做**单决策**级计时（§5），由 `workers=8` 与实测单决策 P95 反推 40 天上限，写入登记后再跑批次 | 在拿到单决策分布前无法给出可靠总上限 |
| GPU | **不涉及** | Role C 是纯前瞻规划器，无学习权重、不用 JAX | — |

⚠️ **禁止**（与规格 §6 一致）：据计时结果挑参数 / 挑 `K` / 挑档位；计时环节**不得**让
效用进来（`resource_timing.measure*` 会递归拒绝效用类字段并抛 `UtilityLeakError`）。

## 4. 计时必须同时记录的东西（否则耗时**无法解释**）

* `environment_record()` 全字段（本机 + 服务器）；
* **运行前后的 `loadavg`**（本次已见 ≈30，必须留痕）；
* 解释器与版本：正式运行 = 项目 `cc_compare` env（`/home/hzeng/envs/cc_compare/bin/python`），
  **不是** §2.1 里的系统 `python3`；
* `warmup` **单独计次且不进统计**（排除编译/缓存冷启动）；
* 单决策分布：`measure_series` 的 `per_decision`（mean / P50 / **P95** / max）；
* `workers` 与亲和性实参（实参，不是"打算用的值"）。

## 5. 建议的执行顺序（**每一步都需你确认**）

1. **核准本文件的 §3 上限**（或给出你的值）⇒ 用下面这一条命令写成登记文件（**校验不过就不落盘**）：

   ```bash
   python CC_Compare/tools/role_c_resource_ceiling.py \
       --workers 8 --affinity 0-7 --total-wall 43200 \
       --cpu-count 96 --mem-gb 265.3 --machine "服务器 /home/hzeng/project/MASKCO-Main" \
       --registered-by "<你的名字>" [--dry-run]
   ```

   * 先加 `--dry-run` 看占用率与校验结论，确认后再去掉它落盘；
   * **不提供任何默认上限值** —— `--workers/--affinity/--total-wall/--cpu-count` 必填，
     漏给就报错（上限是**登记决策**，不能被脚本默认掉）；
   * 四项线程上限缺省 = 全 1（规格点名 `OMP=1`；另三项**漏配**即过度订阅风险）；
   * `--cpu-count` **必须填跑批那台机器**的核数（服务器 96），不是写登记那台；
     核数取登记里的事实 ⇒ 登记在任何机器上都可复验（换机不会误判合法/非法）；
   * 单决策时限**自动取冻结 `time_limit`（10.0）**，不让人随手填（计时必须测"要跑的那个"）；
   * 已存在 ⇒ 拒绝覆盖（重新登记属**资源门变更**，需换 `ceiling_id` 并用 `--force`）。

2. 再做一个**只测时间与资源量**的单决策级计时（在本建议的合成夹具/单实例上，**不看效用**），
   产出 `per_decision` 分布（mean/P50/P95/max）+ 前后 `loadavg`；
   入口 = `role_c_timing.run_timing(work_fn=role_c_timing.make_decision_work_fn(decide_fn, contexts), ...)`，
   其中 `contexts` 来自 `role_c_t_series.run_fixture(..., capture_n=N)` 捕获的**真实冻结**决策点。
3. 由实测 P95 反推 40 天的总墙钟上限，**补进登记**；
4. 之后才谈正式批次（而正式批次本身仍需另行授权 —— 本阶段明令禁止）。
