## 1. 超时语义专项审计（优先级 1，已执行）

### 1.1 用户假说

### 1.2 七条**机械核验**的源码事实

审计器 `CC_Compare/tools/role_c_timeout_semantics_audit.py` 用**源码解析**（不是叙述）
逐条核验；缺一条即失败。全部成立：

| **F2** | `deadline_hit` **不是**独立观测：`forward_value` 初始化 `deadline_hit=False`，内部截止**只在每个场景开始前**检查 | `role_c_forward.py` | 场景循环行 60 → 截止检查行 61 → 订单循环行 69（截断检查**在**订单循环之前 ⇒ 场景内部的长调用不被观察） |

### 1.3 合成反例（轻量、独立、用**真实**函数）

用真实 `shadow_price_budget` / `_run_with_limit` + 一个抛 `DecisionTimeout` 的替身前瞻：

| 情形 | `shadow_price_budget` | `_run_with_limit` |
|---|---|---|
| **前瞻内抛**（模拟 SIGALRM 落在前瞻里） | **正常返回**，`undefined=True`，`lambda_B=None`，`reason='V̂ 求值抛错：单决策超过 0.050s 硬时限 ⇒ 终止并回收'` | **`timed_out=False`**（外层完全看不到超时）；两次前瞻调用都被吃掉 |
| **前瞻外抛**（对照） | 正常返回 `λ=0.0`、`undefined=False`（异常根本没到它） | POSIX：`timed_out=True`；非 POSIX（本机 Windows）：异常直接穿出并注明该平台无硬中断语义 |

⇒ **用户假说成立**：吞没**只**发生在前瞻窗口内（异常是否落在 `future_value_fn` 调用的
`try` 内），而一旦落在里面，**超时计数与拒单原因就被混淆**。

### 1.4 比"模板未更新"更具体的两点（我此前的猜测需要更正）

我在上一轮的猜测是"`last_diag` 停留在**含 `deadline_hit=False` 的初始模板**"。
源码核验后**不成立，且问题更具体**：

1. **`last_diag` 的初值是 `None`，不是含 `False` 的模板**（F3）。
   于是"归档里 `deadline_hit=False`"有**两种不可区分的来源**：
   (a) `last_diag` 是 dict 且其 `deadline_hit` 为 `false`；
   (b) **`forward` 键根本不存在**（`last_diag is None`），我的记录代码
   `fw = d.get('forward') or {}` 于是**默认取到 `False`**（F7 证实记录里没有 `forward` 键）。
   ⇒ 本批 `deadline_hit=false` **既不是"未触发截止"的证据，也不是"触发过但没被观测"的证据**
   —— 它**不可追溯**。
2. **原始抛错信息在决策记录里被结构性丢弃**（F6）：B3 分支不引用 `_d0`，
   留下的是**通用**文案「λ_B 未定义（V̂ 非有限/差分未定义）」，
   与"V̂ 真的非有限"**无法区分**。

### 1.5 超时来源的可恢复性（逐通道判定）

| 通道 | 可恢复？ | 依据 / 局限 |
|---|---|---|
| `shadow_price_budget` 自己的 diag | **可以**（但只靠文案） | `reason` 保留了 `%s` 的异常字符串，`DecisionTimeout` 文案含「硬时限」⇒ 可子串识别；**类型名未保留**，文案改动即失效 |
| `decide_candidate` 的决策记录 | **不可以** | F6：`_d0` 被丢弃，只剩通用文案 |
| `_run_with_limit` 的返回值 | **不可以** | F5：异常被吞 ⇒ 正常返回 ⇒ `timed_out=False` |
| `forward_value` 的 `last_diag.deadline_hit` | **不可以** | F2+F3，且 F7 让它更不可追溯 |
| 进度原件（插桩 `leaf_enter/exit` + 心跳） | **部分** | 能证明「前瞻**没跑完**」（`timed_out`）；**不能**证明「是被 SIGALRM 打断的」 |

### 1.6 因此：`evaluation_status` 与 `timeout_cause` 必须分开

| 字段 | 取值 | 由什么证明 |
|---|---|---|
| `evaluation_status` | `not_entered` / `completed` / `timed_out` | **进度原件**（进入/退出叶子、进入/完成场景数） |
| `timeout_cause` | `None` / **`unknown`** / `SIGALRM_decision_timeout` / `forward_internal_deadline` / `unknown_exception` / `budget_exhausted_inside_forward` | **异常路径证据**（异常**类型** + 抛出点） |

* **未取得证据时一律写 `unknown`**，**不得**默认成某一因；
* `evaluation_status=timed_out` 表示"前瞻没跑完"，**不**蕴含"被硬超时打断"；
* **`deadline_hit=false` 在本批不得作为"未触发截止"的证据。**

### 1.7 本批 8 例：一致性推断（**未闭环**）

归档签名检查（`archive_signature_check`）显示 8/8 **与吞没路径一致**：

| 检查 | 结果 |
|---|---|
| 全部 `boundary = B3_lambda_undefined` | ✅ |
| 全部 `deadline_hit = false` | ✅（但按 §1.4 不可追溯） |
| 全部墙钟略超 10 s（10.001–10.004） | ✅ |
| **每个决策点只进入前瞻 1 次**（本应 2 次：`b` 与 `b − e_o`） | ✅ |
| 每个决策点只进入 1 个场景 | ✅ |
| `P7c` 从未进入（0 个场景跑完） | ✅ |
| 8/8 分区四条件闭合（截断窗口的份额本身合法） | ✅ |

⚠️ **以上是"一致性"，不是证据链闭环**：本批**未归档**原始事件表与异常类型
⇒ **无法区分**「SIGALRM 被吞没」与「V̂ 真的非有限」。
审计器在报告里**强制**带上这句 `explicit_warning` 与 `requires_targeted_run`，
并有回归断言"报告里不得出现'已确认被硬超时打断'这类字段"。

**要定案需要的两件事**（属 §3 的新预注册范围）：
1. 在吞没点**按类型**识别 `DecisionTimeout`（或至少把 `type(exc).__name__` 写进 diag）；
2. 归档原始事件表，使通道 C 可在真数据上二次独立重算。

## 3. 新预注册**设计**（优先级 2：只出设计，**未跑**）

### 3.1 下一版必须归档的字段（用户批准，作为独立复核资格的**硬要求**）

| 字段 | 目的 |
|---|---|
| `raw_events`（`('enter'/'exit', label, ts)` 原始流） | 独立重建 enter/exit 配对与调用栈 |
| `events`（`(label, t_enter, t_exit)` 区间表） | 验证区间嵌套、包含与互斥 |
| `leaf_counts` | 重算 `stages_entered` 与调用数量 |
| `decision_point_digest` | 防止决策点被替换 |
| `timer_origin` / `clock_domain` | 确认时间戳属于**可比较**的时钟 |
| `instrumentation_source_sha256` | 确认插桩源码身份 |
| `event_stream_complete` | 明确是否发生异常或强制截断导致事件缺失 |

### 3.2 A 类的事件丢失处置（SIGKILL 会丢缓冲）

* **事前规定周期性落盘**（或外部事件日志），**不得**依赖进程退出时的 flush；
* 截断时**未闭合**的区间标 **`CENSORED`**，**不得补写退出事件**
  （补写会把"没观测到"伪造成"观测到了"）；
* 落盘粒度必须与 `600 s` 单点上限相容：至少保证"被杀时能定位到叶子与场景"。

### 3.3 B 类的通道 C 验收前提

只有在 **事件流完整** 且 **双通道计量与离线重算符合原规格** 时，
才允许报告"通道 C 的真实数据验收结果"；
否则只能报告"通道 C **不可在本批数据上独立重算**"（本批即属后者）。

### 3.4 若要重测完整 A 类路径，新预注册**先**要明确（用户列的六项）

1. 新的单点上限；2. 总资源上限；3. 固定决策点身份；
4. 截断处理；5. "完整场景"条件；6. 资源耗尽时的**停止语义**。

* 分级上限**可以**作为新协议的一部分，但**不得反向替换**本次 `600 s` 的正式结果；
* **本轮不提高 `600 s`**：现有结果显示"等满整个已注册单点上限仍未完成"，
  直接提高上限可能只是**购买更长的截断时间**。

### 3.5 本设计**明确不做**的事

* **不**启动长跑；**不**改 `600 s`/`12 000 s`/`K`/`10 s`/核集/`workers`/邻域；
* **不**触碰保留种子；**不**进 Phase B、烟测、40 天批次、最终测试；
* **不**自动启动 L3。

### 3.6 优化方案的双验证要求（用户明确）

任何"优化"都必须**同时**验证：

1. **输出语义等价性**（按 REV2 §7 的逐条比对与数值规则）；
2. **计算开销变化**（如实报，含仪器自开销）。

**不得**仅因调用次数高（例如 `route_feasible` 百万级）就认定这些计算可以删除。
